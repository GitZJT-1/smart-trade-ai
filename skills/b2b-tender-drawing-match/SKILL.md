# B2B 招标图纸匹配重命名归档

> 📄 配套技术手册：`b2b-doc-generation` skill 可生成完整的 .docx 版本（品牌色深蓝 #0B2A4A + 金 #D4A853），含全部 19 个陷阱 + 完整参考实现，适合分发给其他 Agent 复刻。模板参考 `references/docx-technical-manual-patterns.md`。

## 触发条件
- 用户给出 JSON 清单（从招标 xls 提取，字段 `№`/`Наименование`/`Кол-во`）+ 图纸库文件夹（多个子目录、多种格式 pdf/tif/jpg/zip/7z/docx），要求按文件名匹配后重命名归档
- 用户说「以 Наименование 作为索引 / 按照文件名称寻找内容相同项 / 重命名为 № 开头 / 放入对应数字序号的文件夹」即本技能

## 用户约定（铁律）
1. **重命名规则**：`{№}-{原文件名}`，前缀**不做零填充**（`99-`、`1165-` 而非 `099-`）；原文件名已有数字序号时保留（`52. Ковш...` → `1165-52. Ковш...`）
2. **归档目标**：文件移到该 Наименование 所属 JSON 编号对应的文件夹（`...\1223588_ISO三分部...\1223588`），先 `os.makedirs(exist_ok=True)`
3. **只匹配文件名文本**：不从图纸文件内部提取图号、不对比文件夹日期
4. **匹配率低要如实汇报**：图纸库与清单重合度可能极低（实测 0.7%），不要为凑匹配放宽阈值制造误报；按用户提供的图纸库实际匹配，能匹配多少算多少，未匹配项原地保留
5. **СБ 总装图纸整夹绑定**（2026-08-13 用户定·铁律）：清单 `Наименование` 末尾归一化为 `СБ`（大小写不敏感 + 前导空格容忍：`СБ`/`Сб`/`сб`；文件夹名可能是拉丁 `CБ`）的项是**总装图纸（сборочный чертеж）**。图纸库中总装图对应一个**以 `СБ` 结尾命名的文件夹**（如 `Блок переходных шин ч. 78-212-00-000CБ/`，内含 `78-212-00-000СБ.tif` 总装图 + 全部 `78-212-XX-XXX.tif` 零件图 + 子装配）。匹配这类项时**不是只归档单个总装图文件，而是把该文件夹全部内容（总装+全部零件+子装配）打包进 `{dest}/{num}/`**。⚠️ 影响面巨大：1223570 有 240 项、1225472 有 263 项以 СБ 结尾（合计约 1/4 清单），旧引擎只按单文件匹配会漏掉整套零件图

6. **图号数字零填充容差（canon 键，2026-08-13 实测铁律）**：招标清单的图号常把末段数字缩写，如清单写 `104-643-00-00СБ` 而库/图纸实际是 `104-643-00-000СБ`（末段 `00` vs `000`）。用 `norm_pn` 精确比较必漏。必须加一层 `canon(pn)`：去 `.сб` 后缀 + 分隔符统一 `.` + **每个纯数字段 `str(int(seg))` 去前导零**（`104.643.00.00` → `104.643.0.0`，`104.643.00.000` → `104.643.0.0`，相等）。此键仅用于 СБ 整夹匹配 + `PAD` 单文件策略，且必须过 `name_related`（词交集≥1）防巧合。⚠️ 不能只对整文件名做 canon——文件夹名带名称前缀（`Барабан приводной ч.104-...`），须先 `extract_part_number` 提取图号再 canon。

## 匹配算法（17 版迭代后的最终配方）

### 1. 图号规范化 norm_pn（关键！）
```python
def norm_pn(s):
    s = unicodedata.normalize("NFKC", str(s)).lower()
    s = s.replace("(", "").replace(")", "").replace("+", "")
    s = re.sub(r"[\s\-_/\\]+", ".", s)   # 分隔符统一 '.'
    return s.strip(".")
```
⚠️ **禁止用 compact()（删光所有非字母数字）比较图号**：`1.8.421` 与 `18421` 会被判为相等 → 大面积误报。必须保留分隔符结构。

### 2. 图号候选提取
- **JSON 侧**（`Наименование` 形如 `名称 ч.图号`）：
  - ① `ч./Ч.` 后图号（`extract_part_number` 正则 `[чЧ]\s*\.?\s*(...)`）
  - ② 名称末尾编号段（如 `Блок шестерен 306-11-04А` 无 ч. 前缀）
  - ③ 名称中带字母前缀的编号段（如 `ALX0013`）
- **图纸文件侧**：
  - ① `ч.` 后图号 ② 文件名开头编号（**长度≥4 才收**，排除 `45.`/`52.` 这类序号）③ 名称中间编号段（如 `46 Блок золотников 1564.08СБ.7z`）
- **过滤**：norm 后长度 **≥4**（v20 从 5 降到 4，`0018`/`0005`/`0002` 等 4 位图号不再被过滤；短编号如 `45`/`52`/`400` 仍排除）

### 3. 匹配优先级（取最优）
1. `PN` — 图号 norm 相等（最强）
2. `NAME` — 名称 compact 相等（去序号前缀后）
3. `VER` — 图号互含（双方 len≥8，标注 `c~jc`，置信度 MED）
4. `REV` — **图号主干相等（版本后缀 -А/-Б 容忍）**：`М4924.00.000-А` ↔ `ч.М4924.00.000-Б` 是同一零件不同改版，应匹配。实现：对 norm 后图号剥掉末尾 `[.-]([а-я]{1,4}|\\d{1,2})$` 后缀再比主干（主干 len≥8 且名称词交集≥1）。⚠️ 只有主干不同才算不同零件：`78-00-00-12` vs `78-00-00-23` 尾号不同 → 拒绝（Чашка ввода 误报案例）
5. `FUZ` — **СБ 后缀容错**：lib PN 末尾有 `.сб` 而 JSON PN 没有（或相反）→ 剥掉 `.сб` 后比主干（len≥4）。典型场景：JSON `ч.306-11-07СБ` ↔ lib `ч.306-11-07`（同一零件，JSON 多标了 СБ）。⚠️ 仅剥 СБ 后缀，不放宽其他差异

### 4. 名称关键词交集验证（防巧合编号）— v20 增强

```python
def get_words(s, min_len=3):
    return set(re.findall(r"[А-ЯA-ZЁа-яё]{%d,}" % min_len,
               unicodedata.normalize("NFKC", s).lower()))

def name_related(lib_base, json_name):
    """v20: 默认 min_len=4；JSON 无 ≥4 字符词时降级到 min_len=3"""
    json_w4 = get_words(json_name, 4)
    if json_w4:
        return len(get_words(lib_base, 4) & json_w4) >= 1
    else:
        return len(get_words(lib_base, 3) & get_words(json_name, 3)) >= 1
```

每条 PN/VER 命中都必须过此关：过滤「图号巧合但名称无关」的误报（如 `Винт натяжной ч.300-00-00` ↔ `В117.00.300.00.000ААА телескоп`）。

⚠️ **v20 核心改进**：原版固定 min_len=4 会漏掉 JSON 名只有短词的项（如 `Вал ч.1.16.43...` 仅含 3 字符词 `вал`）。现在 JSON 无 ≥4 字符词时自动降级到 min_len=3，捞回 `вал`/`ось` 等短词匹配。降级仅在有精确 PN 匹配时触发，不独立用于模糊搜索。

## 复查（用户问「还有没有可以重命名的文件项」时）
1. **先跑严格引擎**（PN/NAME/VER）→ 常得 0，别急着下结论
2. **再补 REV 轮**（剥版本后缀比主干，用 `strip_rev_safe` 防多位数段误剥）→ 上轮实测捞出 1 个真匹配（`Труба нижняя М4924.00.000-А.tif` → 1223588 №98）
3. **宽松候选必须甄别尾号巧合**：名称词交集≥2 + 数字段交集（`\\d{4,}` 才收，`001`/`002` 这类尾号全是噪音）只能当提示，不能当证据；图号主干才是硬证据
4. 汇报格式：候选表（文件 ↔ JSON № ↔ 判定：已归档/排除+理由），并说明为什么没有更多可匹配（图纸源在云端未下载）
5. 确认后执行 REV 轮命中项，走标准验证（回读目标文件夹 + 源库剩余数核对）

## 多项目批量匹配

当同一图纸库目录树服务多个招标项目时（如报价单根目录下的 `3 БФ`/`7 СФ`/`9 ШФ`/`shf_*` 等同时服务 1223588/1224501/1224579），效率最高的模式是 **一次扫描、多清单匹配、统一移动**：

1. **提取所有清单 JSON**：从各项目 .xls/.xlsx 提取 №/Наименование，存为 `items_{tender_id}.json`
2. **一次扫描图纸库**：`os.walk` 所有共享目录，构建文件列表（含 `cands` + `base_c`）
3. **逐文件多项目匹配**：对每个图纸文件，分别尝试匹配每个项目的清单 → 命中则记录 `(project_tag, file, strategy, item_data, detail)`。**关键**：每个文件可能命中多个项目，需要记录完整的命中项目列表（`hit_projects` set），不能命中第一个就 `break`。
4. **按项目分别归档**：按 `project_tag` 分组。**单项目命中**用 `shutil.move`；**多项目命中（交叉匹配）**用 `shutil.copy2` 复制到每个目标项目，源文件保留（或所有项目都处理完后统一删除）。然后各自走 MD5 去重。
5. **交叉匹配验证**：每个交叉匹配文件必须验证在所有目标项目都存在。归档后遍历交叉列表，对每个 `(file, project)` 对确认目标路径存在文件，缺失则从已有归档的项目补复制。

⚠️ 不要在循环中为每个项目独立扫描——20K 文件 × 3 项目 = 60K 次遍历效率极低；一次扫描后多项目并行匹配可压缩到 ~20K 次遍历。

⚠️ **跨项目文件必须各自归档**（2026-08-11 纠正）：同一图号文件命中多个项目清单时（如 `3 БФ` 中的 `Скоба зажима М428.02.07.7z` 同时命中 1225472 №25 和 1223570 №12），**必须归档到所有匹配项目**，不能只给先处理的项目。用户原话：「这些确认被两个项目同时采购的配件就各自归档一份，不要只归档到单个项目，我也没有设置优先级」。实现：① 匹配阶段记录每个文件命中的全部项目列表（`hit_projects` set）；② 归档阶段对单项目命中用 `shutil.move`，对多项目命中用 `shutil.copy2` 复制到每个项目后再决定是否删除源文件；③ 验证阶段检查交叉匹配文件是否在每个目标项目都存在。交叉匹配文件数量必须在报告中标注。

## 跨年份目录去重（同一图号多副本，2026-08-13 实测）

图纸库常有按年份分目录的结构（`kf_crgpm\2023`/`2024`/`2025`、`shf_crlp\Чертежи ЦРОЛП 2022`、`3 БФ\bf_ceo\Годен на 2023 год` 等）。同一图号会逐年重复收录，产生三类冗余，用户要求「同一图号只保留一个，但不误删内容不同的图纸」：

| 层 | 判定 | 动作 | 风险 |
|---|---|---|---|
| **L1 字节级** | MD5 完全相同 | 保留 1 份(最新年份/最大)，其余回收站 | 零风险（内容逐字节相同） |
| **L2 重扫/签名** | 同名 + 图像 dHash≤6 | 保留最佳(签名版>最新年>最大)，其余回收站 | 需加文件名约束防误删 |
| **保留** | 图号前缀相同但**文件名不同**(不同 sheet/零件/改版 `изм.N`) | 全部保留 | — |

### L2 实现要点
- **分组键 = 精确 `norm_pn`**（**禁止 canon 零填充**）：`canon` 会把 `АМ402.17.001`(零件) 和 `АМ402.17.01СБ`(总装) 都归并成 `ам402.17.1` → 大面积误合并。去重必须用不零填充、不剥 СБ 的 norm_pn。
- **图像相似度**：`fitz` 渲染 PDF 首页 / `PIL` 打开图片 → 9×8 灰度 dHash(64bit)。汉明距离 ≤6 = 同一张图（重扫/签名版）；>10 = 不同 sheet/改版。
- **聚类用贪心代表法（非 union-find，2026-08-13 实测）**：union-find 传递闭包会把间接相近（A~B~C 但 A~C>6）误合并。改为按「签名>年>大小」排序，每个文件只挂到【直接 dHash≤6 且全护栏】的代表上，保证每个待删件与保留件**直接**视觉近同。keep-best = 签名版 > 最新年份 > 最大文件。
- ⚠️ **必须叠加「同名」约束**（关键）：dHash 对简单图纸区分度不足——`1068604_06 СБ` vs `1068604_07 СБ`（不同 sheet）dHash 可能 ≤6 被误判同一张。**文件名归一化相等**（去列表前缀 `^\d{1,3}\.`、去 `-signed`、去 ` (N)`、去尾随 `+`、空白折叠）是硬门槛，跨名绝不合并。
- **跨库保护**：同一簇若跨多个顶级库（`3 БФ` vs `14 ШФ ЦРЭП` = 不同客户），绝不合并——各自库必须保留各自副本。
- **改版号冲突保护（2026-08-13 实测）**：同一图号组里 `изм0` vs `изм1` 是不同改版，**绝不能合并**。实现 `rev_of(name)` 提取 `\bизм[.\s]*(\d+)`；两文件 `изм` 号不同 → 跳过；一个带 `изм` 一个不带 → 也跳过（保守）。
- **文档类型冲突保护（2026-08-13 实测）**：`СБ`(总装) / `СП`(明细/спецификация) / `деталировка` / `спецификация` 是不同文档，dHash 可能仍判近同。提取 `type_of(name)` 关键词集，两文件类型集不同 → 绝不合并。例：`секция раздающая ДМ ч.1069098сб` vs `1069098 - изм0 - секция раздающая`（СБ vs изм0）必须都留。
- **渲染失败一律保留（铁律）**：`fitz`/`PIL` 打不开的文件（损坏 PDF/TIF、DecompressionBomb 超限、截断 EXIF）**绝不下删除结论**，宁可多留不误删。实测 1032 组里 779 份渲染失败，全部原样保留并单独报告。
- **效率：按 MD5 去重后再渲染**：同 MD5 = 字节完全相同，一组里多个文件共享一次渲染结果。用 `md5 → (dhash,res)` 缓存，1032 组 4522 文件只渲染 2931 个唯一 MD5，节省 ~1/3 时间。
- **回收站**：`send2trash` 常缺失，用 ctypes `SHFileOperationW`（`FOF_ALLOWUNDO`），成功返回 0。返回 2 = 文件已被删（幻影组，见下）。

### ⚠️ 图号归一化撞车：同名不同件（2026-08-13 实测·高危）

`norm_pn` 会把**不同零件**归并到同一键：`втулка ч.1564.03.001`（втулка=衬套）和 `щека основная 1564.03.01сб`（щека=颚板）都归到 `1564.3.1`。实测 1032 组里 **522 组（>50%）内是「干净文件名 ≥2 个」的不同图纸**，其中大量是这种同名不同件。这就是为什么**绝不能按图号硬删**——必须靠 dHash + 文档类型 + 改版号三重护栏先区分「同一张图重扫」还是「不同图纸」。只有视觉近同 + 同名 + 同类型 + 同改版才合并。

### ⚠️ 嵌套年份目录双遍历陷阱（2026-08-13 发现）
年份目录检测 `re.search(r'\b20(2[0-9]|3[0-1])\b', dirname)` 会**把年份目录的子目录也当成年份目录**（如 `2023\0. Корректировка 3-й квартал 2023\`、`2023\19. Стяжка ... на 2023 г.\` 都含 "2023"）。`os.walk` 每个年份目录时会**重复遍历嵌套子目录** → 同一文件被 append 两次 → 计数虚高（实测 68 个年份目录中 12 个是嵌套的，虚增 ~776 份）且 MD5 分组出现 `[F, F]` 幻影组导致 `send2trash` 返回码 2(文件已删)。**修复**：只保留「顶层年份目录」（祖先中无其他年份目录），或遍历时用 `seen` 集合按真实路径去重。

## 执行与验证
1. 先 dry-run 输出全部候选清单（含 Q 等级 + 目标路径），人工核验无名称无关项后再执行
2. 执行：`shutil.move`；目标同名时 **MD5 内容比较**——相同则 SKIP，不同则加 `_v2` 后缀（同一零件在 2022/2023/НЗЧ 等多子目录常有重复副本）
   - **目标分配按 `(tag, num)` 去重**（2026-08-13）：同一文件既被单文件匹配、又落在某 СБ 文件夹内命中同一清单项时，两路会给同一 `(tag, num)`，须用 set 去重，否则单目标误判为多目标触发多余 copy
   - **单目标 move / 多目标 copy**：同一源文件命中多个 `(tag, num)`（跨项目或同项目不同行项，如 `Стойка звездочки` 同一总装被 1224579 №395/396 + 1225472 №1033/1034/1035 五行采购）时，`shutil.copy2` 复制到每个目标后再删源；单目标直接 move
   - **平放→子夹合并**：原单文件项（平放 `{num}-xxx`）在 СБ 绑定后变多项时，须把平放文件移入 `{num}/` 子文件夹，否则同一项既有平放又有子夹，违反「多文件入子夹」规范
3. 验证（用户规则：日常任务以交付物为准，不重跑全量 pytest）：
   - 回读目标文件夹，逐一核对 `{№}-` 前缀 ↔ JSON № ↔ Наименование 图号/名称关键词
   - 确认源图纸库剩余数 = 原数 - 移动数
   - 只跑针对性冒烟 pytest（如 `uv run pytest tests/test_extract_7z_scripts.py -q`）
4. 清理：所有 tmp_*.py 一次性脚本删除，工作区零残留

## 陷阱
- **short-number 串扰**：`45 C-139.01 СБ` 的开头 `45` 会被误当图号匹配 JSON 里以 `45` 结尾的项 → 长度≥5 + 排除纯序号开头
- **compact 陷阱**：见上，图号比较永远用 norm_pn
- **多副本冲突**：同一图号文件出现在多个子目录 → 重命名后目标同名，用 MD5 去重/`_v2` 区分，不要盲目覆盖
- **`ч.` 大小写与空格**：`Ч.`/`ч.`/`ч ` 都要处理；`Э-85085+` 的 `+` 尾缀 norm 时去掉
- **尾号巧合误报**：宽松匹配中 `001`/`002`/`003` 这类 2-3 位尾号会让毫不相干的项互相匹配（`Втулка защитная ч.170.00.001` ↔ `Втулка дистанционная ч.68-1769-03-003` 等），名称词交集≥2 也拦不住（如「втулка+защитная」同名不同件有十几条）。数字段交集必须 `\d{4,}` 起收，且仅当辅助证据
- **无 ч. 前缀的图号**：大量 JSON 项（如 `Венец СМ6001.01.00.001`、`Блок шестерен 306-11-04А`）图号不在 ч. 后 → 必须提取名称末尾/中间编号段，否则漏掉近半清单
- **"черт." 前缀**：俄语 `черт.` 是 `чертеж`（图纸）的缩写，与 `ч.` 同义。文件名如 `черт.19574.tif` → 图号 19574。`extract_part_number` 的正则 `[чЧ]` 只匹配单字符 `ч`，`черт` 中 `ч` 匹配后 `ерт` 不是图号开头 → 漏报。修正：正则在 `[чЧ]` 后增加 `(?:ерт)?` 可选段
- **图号候选提取中大小写敏感**：`lib_pn_candidates` 的编号段正则 `[A-ZА-ЯЁ]{0,4}` 只匹配大写。文件名 normalised 为小写后（如 `штепсельный разъём дрз-76`），`дрз` 不匹配 → 图号 `ДРЗ-76` 被漏掉。修正：字符类加小写 `[A-Za-zА-Яа-яЁё]`
- **REV 后缀无分隔符**（2026-08-10 发现）：文件名 `ч.492676А Винт кюбеля` 中版本后缀 `А` 直接追加在图号 `492676` 末尾，无 `-` 或 `.` 分隔。原 `strip_rev` 正则 `[.-]([а-я]{1,4}|\\d{1,2})$` 因缺少分隔符而无法剥离 → 图号 `492676а` 与 JSON `492676` 被判不相等（REV 漏检）。修正：`strip_rev` 改为 `[.-]?([а-я]{1,4}|\\d{1,2})$`（分隔符可选）
- **REV 多位数段尾号误剥**（2026-08-11 发现）：`strip_rev` 的 `\\d{1,2}$` 会贪婪匹配 3 位数的后 2 位——`78.00.00.036` → 匹配 `36`，剥成 `78.00.00.0`；`78.00.00.033` → 匹配 `33`，剥成 `78.00.00.0`。两者「主干」相等 → пробойник D10（№8）误匹配 пробойник 5（另一规格）。修正：`strip_rev_safe` 用 `(?<!\\d)\\d{1,2}$`（负向后顾），确保数字后缀前无相邻数字——`036` 中 `6` 前有 `3` → 不匹配 → 保留完整。⚠️ 残余风险：纯 2 位尺寸变体（如 `А1025.416.16` vs `А1025.416.19` → 剥 `16`/`19` 后主干相同）仍会误报，需 `name_related` + 人工甄别。实现替换为：\n```python\ndef strip_rev_safe(n):\n    m = re.search(r\"[.-]?([а-я]{1,4}|(?<!\\d)\\d{1,2})$\", n)\n    if m: return n[:m.start()]\n    return n\n```
- **纯名称匹配项无 ч. 前缀**（2026-08-10 发现）：JSON 项如 `ГАЙКА ЛАТУННАЯ ЭСК.ЛПСК(3)` 没有 `ч.` 前缀 → 引擎的图号候选提取失败，`json_pn_candidates` 仅产出一个 norm 后长度刚好为 5 的候选（`лпск3`）。文件名如 `2. Гайка Латунная ЭСК.ЛПСК (3)` 中括号内有空格差异 → compact 不完全相等 → NAME 策略也失败。修正：图号候选不足时降级到 compact-name 子串匹配（≥6 字符公共子串 + 词交集≥1）
- **同 PN 多行项**（2026-08-10 发现）：招标清单中同一产品有多个行项（不同数量），如 №39/40 共享 `23.1162.00.000СБ`、№92/93 共享 `ДРЗ-76`。引擎 `json_by_pn` 索引将所有匹配 JSON 项分组，但在 VER/REV 阶段只取 `jl[0]`（首个），导致同 PN 的其他行项被遗漏。修正：当 PN 匹配 `json_by_pn[c]` 返回多项时，为每一项分别产出命中（而非只取第一项）
- **COM .xls 格式写入不可靠**（2026-08-10 发现）：Excel COM 设置 `Interior.Color/ColorIndex` 后 `wb.Save()`，同 session 内回读正确，但关闭重新打开后格式全部丢失。**只影响 .xls 格式**。解决：COM 读示例行颜色 → COM `SaveAs FileFormat=51` 转 .xlsx → openpyxl 着色写入。详见 `references/excel-annotation.md`
- **共享图纸库跨项目混存**（2026-08-11 发现）：报价单根目录的共享图纸库（`3 БФ`/`7 СФ`/`9 ШФ`/`shf_*` 等）同时服务多个招标项目（1223588/1224501/1224579）。扫描一次、匹配多个清单效率远高于逐项目重扫。⚠️ 项目自带的 source 子目录（如 1223588 下的 `bf_ceo`/`sf_cap`）可能是从共享库提取的子集，其中的未匹配文件可能属于其他项目——不要误判为匹配率低。⚠️ 同一图号文件可能命中多个项目清单 → 须一次遍历完成所有项目的匹配判断再统一移动，避免先匹配的项目移走后其他项目漏检
- **FU2 前缀匹配大面积误报**（2026-08-11 发现·禁止使用）：尝试「图号前缀段相等 + 最多 1 段差异」的 FU2 策略在 1224501 上产生 **51/51 全部误报**（如 `600.14.003` vs `600.17.00.001` 首段相同但完全不同零件）。**绝对不要启用任何基于「图号前缀+段数容忍」的模糊策略**——俄标图号首段往往是系列号，不同零件共享首段极其常见。
- **归档平放 bug — 文件未入 №/ 子文件夹**（2026-08-11 发现·已修复）：`match_drawings.py` 执行段的 `dst = os.path.join(dest_dir, f"{num}-{e['fn']}")` 将文件直接放在了归档根目录（如 `归档/4-Барабан пересыпной ч.0018.pdf`），而非 `归档/4/4-Барабан...pdf`。根因：缺少 `item_dir = os.path.join(dest_dir, num)` 中间层。**v20 修复**：每项先 `os.makedirs(os.path.join(dest_root, num), exist_ok=True)`，再将文件移入。⚠️ 发现已平放的旧文件时，用脚本将其移入对应 `№/` 子文件夹（而非重跑匹配——图纸源库文件可能已被移走）。\n- **尺寸尾缀冒充图号**（2026-08-11 发现）：短字母+数字组合如 `L-650`（norm=`l.650`, len=5）会同时出现在 JSON 和 lib 的非 ч. 候选提取中，造成不同零件因同尺寸而误匹配（如 `Ось ч.СС4001300001 (.L-650)` ↔ `Ось ч.СС40.013.00.001 (G-20.L-650)` 是完全不同的轴）。修正：对于非 ч. 来源且 norm 后长度 ≤6 的候选，要求 `name_related` 达到 ≥2 词交集才采纳，或直接排除纯字母+数字（无 Cyrillic 字符段）的候选。
- **图纸在 MinIO 未下载**（2026-08-11 发现）：招标邀请函（如 `Приглашение к отбору ... .docx`）中可能含 MinIO 登录凭据（Логин/Пароль）。当匹配率极低（<30%）且大量 ч. 图号在本地库中不存在时，先检查邀请函中是否标注了图纸托管地址——很可能根本没下载到本地。此时优先下载图纸而非反复调整匹配参数。

## 清单 Excel 标注（后处理）

匹配+归档完成后，用户可能要求「按示例标注已匹配的行」。用户在 Sheet2 某一行手动改了 A 列（№）和 B 列（Наименование）的底色+粗体作为示例，要求对所有已匹配项执行同样标注。

### ⚠️ 关键陷阱：COM 直接写 .xls 不可靠

通过 Excel COM 设置 `Interior.Color/ColorIndex` 后 `wb.Save()`，同 session 内回读正确，但**关闭 Excel 后重新打开格式全部丢失**。正确方案：

1. **COM 读示例行颜色**（`Interior.Color` / `ColorIndex` / `Font.Bold`）— xlrd 的 formatting_info 对某些版本读数不准
2. **COM 转 .xls → .xlsx**（`SaveAs FileFormat=51`）
3. **openpyxl 着色**（`cell.fill = copy(example_fill)` + `cell.font = copy(example_font)`）— 可靠持久化

详细实现见 `references/excel-annotation.md`。
