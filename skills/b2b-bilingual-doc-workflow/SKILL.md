# 双语外贸文档处理工作流（俄/英）

## 场景概述

俄罗斯/乌克兰客户（典型如 ПАО «НЛМК» 新利佩茨克钢铁）发来的合同/规格书/图纸，俄英双语混排。两种结果需求：

- **工作流 A**：客户合同/规格书 PDF → **发货文件**（发票 docx + 箱单 docx + 报关单 xls）— 信息与合同一致、格式与模板完全对应
- **工作流 B**：客户拍品清单 XLS + 图纸 ZIP → **询价表 XLS**（供与工厂技术对接报价）
- **工作流 C**：客户工程图纸（TIFF/PDF 扫描件）→ **OCR → 翻译 → 询价表 / 注释对照表 / 带注释图**（v2.0.0 起并入原 `customer-drawing-to-rfq` 技能全部内容）

## 铁律

1. **信息以源文件为准，禁止编造** — 价格/数量/日期/合同号/规格书号逐字核对，不确定就标 `[待补充]` 问用户
2. **格式以模板为准** — 表头、列序、俄英双语结构必须与用户提供的模板完全一致
3. **俄语/乌克兰语品名保留原文**，附加贴合行业的中文翻译，格式如 `Втулка ч.4-435281 | 衬套 件号 4-435281`
4. **单价/总价在报价前留空**，不得猜测

## 文件识别

| 输入 | 特征 | 处理 |
|---|---|---|
| 文字型 PDF | `get_text()` 非空 | 直接提取 |
| 扫描型 PDF | `get_text()` 为空（0 chars） | 渲染 300dpi PNG → OCR（rus+eng） |
| 俄语 XLS | Наименование, Кол-во, Поставщик | xlrd 直读 |
| 乌克兰语 XLS | Найменування, Кіл-ть, Одержувач（含 і/ї/є 字符） | xlrd 直读，按俄语词根翻译 |
| 图纸 ZIP | 每个零件一个子目录 `N-名称 ч.件号` | 解压后与清单 Lot 一一映射 |

## 工作流 A：合同/规格书 → 发货文件（发票 + 箱单 + 报关单）

### A1 读取合同（多页处理 + OCR + 字段提取 一条命令）

```bash
PY="$SKILL_DIR/.venv-skill/Scripts/python.exe"
"$PY" "$SKILL_DIR/scripts/ocr_pdf.py" "C:/.../4600114993.pdf" --out "C:/.../ocr_out"
```

脚本自动完成：
- **遍历所有页**（修复旧版只看 doc[0] 漏条款页的 bug）：每页 `get_text()` 判文字/扫描，混合文档分别处理
- 扫描页 300dpi 渲染 PNG → tesseract OCR（rus+eng，`--tessdata-dir` 防中文路径乱码）
- 字段提取：宽松锚点 + 特征数字兜底（合同号 16-20 位、规格书号 10 位、金额俄式小数点归一化）
- 输出 4 个文件：`ocr_full.txt` 逐页全文 / `pages/page_NN.png` 渲染图 / `fields.json` 字段+来源页 / `verify_list.txt` 待核清单

字段表（自动提取）：规格书号 Спецификация / 合同号 К договору № / 招标号 Tender / 总金额 Итого сумма без НДС / 币种 Валюта / 交货条款 Условия поставки (DAP) / 付款条款 Условия платежа / 交货期 Срок поставки / 合同日期 от / 供应商 Поставщик / 买家 Покупатель / 制造商 Завод изготовитель

### A1.5 字段交叉校验（vision 双路径，当前环境自动降级）

ocr_pdf.py 已把低置信度/长数字字段写入 verify_list.txt。核对方式按可用性降级：

- **路径 1（推荐，工具可用时）**：用 Hermes `vision_analyze` 加载 `pages/page_NN.png`，逐项核对 verify_list 中的字段（长数字 OCR 常把 1→7、0→8 认错，vision 直接读像素最可靠）
- **路径 2（当前 deepseek 模型 + Gemini key 免费配额为 0，自动降级）**：只核对 verify_list.txt 列出的条目（通常 8-12 条），不是全文——比旧版全人工校对快一个数量级
- 修正字段后更新 fields.json（直接编辑该文件即可）

⚠️ 已知环境事实：`vision_analyze` 工具在当前 deepseek provider 下报 image_url 不兼容；`.env` 的 GOOGLE_API_KEY 认证有效但免费层配额 limit:0（429）。两条 vision 路都不可用时走路径 2。将来任一可用，优先路径 1。

### A3 定位模板 + 结构 dump

- 用户提供「发货文件」目录，内含 `*发票.docx`、`*箱单.docx`、`*报关单.xls`
- **模板只提供格式骨架，主体信息一律取自合同** — 模板里可能是别的公司名（如 Shenyang BYO），必须替换成合同中的实际供应商/买家
- **新模板首次使用跑一次 dump**（替代人工记录结构，产出类似 references/sample-formats.md 的档案）：

```bash
"$PY" "$SKILL_DIR/scripts/dump_template.py" "C:/.../新模板.xls" --cells --out struct.md
"$PY" "$SKILL_DIR/scripts/dump_template.py" "C:/.../新模板.docx" --out struct.md
```

### A3.5 生成策略判断（先判同订单，再选策略）

- **同订单**（模板规格书号/合同号与合同一致，如 26BY008 ↔ 4600114993）：直接复制模板 + 程序化字段校验（A7）即可 — 生成结果与模板一致是**预期行为**，勿为"显得在生成"而从零构建合并单元格 docx（易错、格式退化）
- **异订单/新合同**：套模板骨架，逐字段替换为合同提取的数据
- 合同未载明字段（毛净重/体积/HS 编码/信用代码/申报要素）→ 沿用模板同订单已验证数据，交付报告**注明来源**（来自合同 vs 沿用模板）

### A4 生成发票（docx）

python-docx 复刻模板表格（典型 9 行 × 5 列，俄英双语）：

- 供应商/买家：俄语名 + 英语名 + 地址（双语分行）
- Terms of delivery / Условия поставки：DAP ...
- Country of origin: China / Страна происхождения: Китай
- Terms of Payment / Условия оплаты
- 表头：`Marks & numbers//Наименование и номера | Number & kind of packages, description of goods//Количество и вид упаковок, описание товара | Quantity//Количество | Unit price//Цена | Amount//Сумма`
- 商品行：`编号/俄语品名/规格` | 数量 | 单价 | 金额
- 结尾：`TOTAL /ВСЕГО: ¥金额` + 供应商名称 + 日期

### A4.5 发票商品行对齐构造（用户 26BY009 手动定稿版，以此为准）

**模板原始结构**：R7 只有 2 个 tc —— C0 空 + C1 跨 4 列大单元格（gridSpan），商品行/Total/落款/日期全在 C1 内按段落排布。模板本身是「p1 代码 + p2 品名 + p3 数字行」三段式（数字独立一行、数量右对齐@40-42）。

**用户定稿偏好（26BY009 手动修改确认）**：**品名与数字合并到同一段**——p1 代码行 + p2「品名 + 空格推到数量列 + 数量 + 10 空格 + ￥单价 + ￥金额」，删除独立数字行。列位（0 基，品名 29 字符时实测）：

```
p1:  代码（'1185118'，单行）
p2:  品名 0-28（'Блок источника света RX-40 IR'）
     + 空格填充到 45（数量列起点：填充量 = 45 - len(品名)，品名 29 → 16 空格）
     + 数量左对齐（'3' @45）
     + 10 空格（46-55）
     + ￥ @56 + 单价 10 宽左对齐（'41000     ' @57-66）
     + ￥ @67 + 金额左对齐（'123000' @68-73）
p7+: TOTAL /ВСЕГО: ￥金额
     供应商名 + 日期（日期无尾部填充）
```

**通用公式**（品名长度 L ≤ 45 时）：`品名 + ' '*(45-L) + str(qty) + ' '*10 + '￥' + str(price).ljust(10) + '￥' + str(amount)`。数量列固定 45、￥固定 56/67 —— 品名变长时空格数自动减少，列位不动。

**构造方式**：p2 保留 run 结构按边界分配（run0=品名、run1=空格+数量、run2=10空格、run3=￥、run4=单价、run5=￥、run6=金额）；全表替换用段落级（合并 runs 后 replace 完整词再写回）——w:t 级替换对跨 run 文本（日期 '21'+'.0'+'7'+'.2026'）无效。

### A5 生成箱单（docx）

- 抬头：供应商公司名 + 地址；标题 `Packing List` / `Упаковочный лист`
- `TO MESSRS/К ГОСПОДАМ:` 买家名 + 地址（俄+英）
- `Contract/Договор No. [合同号]  Date/Дата: [日期]`
- `Specification/Спецификация No. [规格书号]` ← 来自合同 A2
- `Terms of delivery: DAP ...` + `Country of origin: China`（双语行）
- 表格 7 列：`Description of goods//Описание товаров | Qty//Кол-во | Unit//Единица измерения | Package//Упаковка | N.W.(kg)//Вес нетто | G.W.(kg)//Вес брутто | Volume/m3//Объём/м3`
- `Total//Всего` 行：数量/件数/毛净重/体积合计
- 结尾：供应商名 + 日期
- 毛净重/体积合同通常没有 → 与用户确认或按经验估算并注明

### A6 生成报关单（xls）

**xls 旧格式必须用 xlutils.copy 复制模板再改单元格**（保留海关格式），openpyxl 不支持 .xls。用工具箱直接做：

```bash
# 先 dump 模板拿坐标 → 写 fill_spec.json（{"sheet":0,"cells":{"行_列":值}}）→ fill
"$PY" "$SKILL_DIR/scripts/xls_tpl.py" dump "C:/.../26BY008报关单.xls" --json > coords.json
"$PY" "$SKILL_DIR/scripts/xls_tpl.py" fill "模板.xls" "输出.xls" fill_spec.json
```

或 import 方式（**必须传 rb 保留原格式**，否则 write 默认样式会覆盖字体/对齐/边框）：

```python
import sys; sys.path.insert(0, r"SKILL_DIR/scripts")
import xls_tpl
rb = xls_tpl.load_template("模板.xls")        # formatting_info=True
wb = xls_tpl.copy_rb(rb)
cells = {(15, 0): "合同号/规格书号", (21, 1): 9031900090.0, ...}
xls_tpl.write_cells(wb, 0, cells, rb=rb)      # rb 传入 → 逐格保留原 XF 格式
wb.save("输出.xls")
```

关键单元格（中国海关标准格式，29行×12列，见 sample-formats.md 坐标）：

| 单元格 | 内容 |
|---|---|
| 收发货人/生产销售单位 | 供应商中文名 + 统一社会信用代码 |
| 贸易国(地区)/运抵国 | 俄罗斯 |
| 境内货源地 | 沈阳 |
| 成交方式 | DAP（来自合同条款） |
| 合同协议号/规格书编号 | `合同号/规格书号` |
| 件数/包装种类/毛重/净重 | 与箱单一致 |
| 商品行 | 项号 \| 商品编号(HS) \| 商品名称、规格型号 \| 数量及单位 \| 最终目的国 \| 单价 \| 总价 \| 币制 \| 征免 |
| 申报要素 | 1:品牌 2:出口享惠 3:外观 4:... 5:规格尺寸 6:材质 7:是否硫化 8:品牌 9:型号 10:GTIN 11:CAS 12:其他（来源：合同+图纸） |

**HS 编码、统一社会信用代码、毛净重、体积等合同里没有的字段 → 标 `[待补充]` 并列出问题清单问用户，禁止编造。**

### A7 三单一致性校验（程序化，不靠肉眼）+ 校验报告

```bash
"$PY" "$SKILL_DIR/scripts/validate_3docs.py" \
  --contract ocr_out/fields.json \
  --invoice "[单号]发票.docx" --packing "[单号]箱单.docx" --customs "[单号]报关单.xls" \
  --report "[单号]三单校验报告.md"
```

- 校验项：合同号/规格书号三单一致、发票金额=合同总金额（优先 TOTAL 行，防单价误判）、箱单与报关单数字互通、合同关键编号全覆盖
- **校验报告是交付物的一部分**，随三单一起给用户（证据链）
- 空白归一化已内置：docx 公司名用不换行空格 `\xa0`（`Shenyang\xa0BYO...`），直接 `in` 匹配必失败，脚本先 `re.sub(r"[\xa0\u2007\u202f\s]+", " ", s)` 再比
- 退出码 0=通过 / 1=有不一致（报告照常输出，人工修正后重跑）

## 工作流 B：拍品清单 + 图纸 → 询价表

### B1 读拍品清单（xls）

xlrd 读取。典型列（乌克兰语，注意与俄语区分）：

| 列 | 原文 | 含义 |
|---|---|---|
| A | Lot | 序号 |
| B | Одержувач | 收货方（保留原文，如 ДФ НИКОТЬЮБ (трубные цеха НТЗ)） |
| C | Найменування ТМЦ | 品名（俄语词根，如 Втулка ч.4-435281） |
| D | ОВ | 单位（шт = 件） |
| E | Кіл-ть | 数量 |
| F | Мінімальна ціна | 最低价（通常为 0/空，**不写入询价表**） |
| G | Додаткова інформація | 附加信息 |

语言判别：乌克兰语用 `і/ї/є` 字符与 `Найменування/Кіл-ть/Одержувач`；俄语用 `Наименование/Кол-во/Поставщик`。翻译按俄语词根走（查 scripts/glossary.json）。

### B2 解压图纸 ZIP + 建立映射

- 子目录名模式 `N-品名 ч.件号` ↔ 清单 Lot N 一一对应（如 `1-Втулка ч.4-435281` ↔ Lot 1）
- 每项内含 JPG/PDF/TIF 图纸（TIF 多为 300dpi 扫描件），处理方式见下方 **B2.5 图纸 OCR 处理**
- 解压后与清单 Lot 一一映射；映射失败时列出无法映射的目录名与清单人工比对（可能子目录名缺 ч.件号）

### B2.5 图纸 OCR 处理（TIF→PNG→Tesseract，OCR.space 兜底）

**输入识别**：图纸文件常为 TIFF 扫描件（微信/邮件传输，命名 `img_*.tif` / `图纸*.tif`）、JPG/PNG 照片、PDF 扫描件（按扫描文档处理）。检查用户当前目录或公司 `产品规格/` 目录。

**Step 1 — TIF → PNG 转换**（Pillow；Windows 系统 pip 可能被锁，一律 venv）：

```bash
uv venv --python 3.14 && source .venv/bin/activate && uv pip install pillow
```

```python
from PIL import Image
img = Image.open("drawing.tif")
if img.mode in ("CMYK", "RGBA", "P", "LA"):   # 灰度/调色板也要转 RGB
    img = img.convert("RGB")
elif img.mode == "L":
    img = img.convert("RGB")
img.save("drawing.png", "PNG")
```

**超大片幅（decompression bomb）**：传真/扫描管线可能产出 1.8 亿像素级 GIF/JPG（如 11262×15950）。Pillow 默认限制 ~178MP 会抛 `DecompressionBombError`，打开前先 `Image.MAX_IMAGE_PIXELS = None`；GIF 多帧取面积最大帧，存 PNG（避开 GIF 调色板问题）。

**Step 2 — OCR 引擎**（优先本地 Tesseract，无则 OCR.space 兜底）：

- **Tesseract（Windows winget 免管理员）**：`winget install --id Tesseract-OCR.Tesseract --silent --accept-source-agreements`（~50MB，timeout≥180s）；俄语包 `curl -L https://github.com/tesseract-ocr/tessdata_fast/raw/main/rus.traineddata -o rus.traineddata` 放入 tessdata 或用户可写目录
- **中文用户名铁律**：`C:\Users\周家同` 这类中文路径会让 `TESSDATA_PREFIX` 传给 tesseract.exe 时乱码（"does not exist, ignore it"）→ **永远用 `--tessdata-dir /tmp/tessdata`**，不设环境变量
- 运行：`tesseract drawing.png stdout -l rus+eng --tessdata-dir /tmp/tessdata`
- **OCR.space 兜底**（无 Tesseract 时）：图缩到 max 1600px、JPEG q85 压到 <1.5MB（免费限额），`urllib.parse.urlencode` 构造 POST（勿手拼 `+` 拼接，400 错误元凶）；超时 120s；`detectOrientation: True` 防扫描图旋转；混排默认 `language="eng"`，纯西里尔换 `"rus"`

**OCR 参数**（工程图纸）：

| 参数 | 设置 | 理由 |
|---|---|---|
| 语言 | `-l rus+eng` | GOST 图纸常俄英双语标注 |
| PSM | 默认 3；乱码时 `--psm 6` | 混合文本+尺寸标注布局 |
| 标题栏 | 裁剪右下区域放大 12-16x，psm 6/10 | 小字缩写密集 |

**Tesseract 常见数字误读（工程图纸）**：

| OCR 输出 | 应为 | 原因 |
|---|---|---|
| `70.` | `10.` | "1"和"0"粘连 |
| `5.*` | `3.*` | "3"在扫描件里像"5" |
| `То.` | `10.` | 西里尔 Т 像 1 |
| `S16.` | `6.` | 相邻英文 S 串行 |

编号列表（如技术要求 1-10）必须对照预期模式人工核验。

**批量处理**：招标批次循环所有零件子目录（46 文件/25 Lot ≈ 2 分钟），不要一次一张。

### B4 提取单重/关键参数（图纸标题栏固定打法）

- 从图纸标题栏提取重量（俄语 `Масса` / `Вес`，英语 `Weight`）
- **固定打法**：扫描 TIF → 渲染 300dpi PNG → 裁右下角标题栏区域 → OCR 定位 `Масса/Вес` 行 → 提取数值
- **标题栏 Масса 格定位（483168 实测）**：ГОСТ 2.104 小标题栏中 `Лит|Масса|Масштаб` 三小格在标题栏第一行最右侧（相对图坐标 x≈0.885-0.995、y≈0.795-0.86），值行在其正下方；不同图纸标题栏 y 起点差异大（0.75-0.83），先扫描右下区域暗像素行分布定位，再裁剪放大 12-16x OCR（psm 6/10）
- **表格式系列图纸标题栏 Масса 空白（关键坑）**：一个图号覆盖多规格的系列图纸（如 `Таблица размеров оправок ХПТ-90` 芯棒尺寸表，图号 Т3-20-К-08А 系列），标题栏 Масса 格**通常留空**——单重必须查图纸内**尺寸表**（表含 `Масса` 列，按规格行取值，如 70х60→19,5 kg），表里没有的定制规格（如 45х26,5/65х57）只能沿用客户清单值并标 `[待核]`
- **Масса 格空白验证**：OCR 反复读不出数字时，把该格二值化转 ASCII 像素图，无字形 = 空白（不要继续浪费时间 OCR）
- 标题栏文字小、缩写多，OCR 结果用 vision 交叉验证（A1.5 同款双路径：可用则 vision，不可用则人工核对）
- **同件号多张图纸交叉验证**：同一 ч.件号 出现多次取一致值，不一致标 `?` 人工定
- 无法确认的标 `?`（样例中 Прокладка 单重即为 `?`）

### B4.5 ⚠️ 材质标准必须以图纸标题栏为准（Interpipe 乌克兰招标教训）

2026-07-31 用户明确纠正的偏差（483168 询价表重做教训）：

- **乌克兰 Interpipe 图纸材质标准是 ДСТУ（乌克兰国家标准），不是俄罗斯 ГОСТ**：
  - 弹簧钢 60С2ХФА → 图纸标 **ДСТУ 8429:2015**（≠ ГОСТ 14959-79）
  - 工具钢 9ХС → 图纸标 **ДСТУ 7807-2000**（≠ ГОСТ 5950-73）
  - 45 钢 → 图纸标 **ГОСТ 1050-62**（≠ 1050-88）
  - 牌号后缀不能丢：**60С2ХФА-Ш**（电渣重熔）≠ 60С2ХФА
- **禁止凭常识/经验编造材质**：Lot 8 定径模曾写"模具钢"（编造），图纸实际是 60С2ХФА-Ш 弹簧钢。每个 Lot 的材质必须来自该图纸标题栏 OCR（tb_*.txt 或全图尾部），无法确认就写"按图纸"并列入待核项
- **图号以图纸标题栏为准**：zip 文件夹名/清单名可能简化（如清单 Т3-20-К-08，图纸 Т3-20-К-08А），物料编码列用图纸图号
- **结构对齐客户清单模板**：询价表 xls 采用客户清单的 10 列结构 `Lot | Receiver | Name | 中文翻译 | Units | Quantity | 单重 | 单价 | 总价 | 工期`（xlwt/xlrd 处理 .xls），不要擅自换成公司 8 列结构
- **列数/表头=自己的逻辑，单元格内容=模板逻辑（2026-07-31 最终裁决）**：客户清单模板常有表头错位（9 列头 / 10 列数据，中文翻译落到 Units 表头下、Units 丢失）——**表头修正为 10 列对齐即可，数据单元格必须逐格沿用模板原值**：中文翻译用客户清单原文（不追加材质注释），单重沿用模板值（含文本格式如 `16,8`），单价空、总价 `0.0`、工期空。图纸 OCR 得到的材质/图号/技术要求写入独立的核对报告（md），不进询价表内容列
- 单重来源要区分：图纸标题栏确认 vs 清单沿用（9/12 项图纸常不标单重），沿用值必须标注"待与客户确认"

### C1 首选：OCR → 注释对照表（用户自行加图，Approach 6A）

### C2 自动内联标注（Approach 6B，PIL）

仅当用户要求自动标注且 C1 未被拒。Pillow + Windows 中文字体（绝对路径 `C:/Windows/Fonts/msyh.ttc`，先 `os.path.exists()` 验证；Python 3.14 相对路径解析异常）。

## 翻译规范（v1.1 新增，统一风格）

1. **件号格式统一**：`件号` + 空格 + 原编号原样保留（含引号/斜杠/点），如 `密封皮碗 件号 НТ.ГП.SMS/13" 3/8.15225342 装配件`
2. **英寸标记**：`13" 3/8` = 13又3/8英寸，中文统一写 `13又3/8英寸`（不再出现"又 3/8 寸"混写）；纯数字后缀 `244,5` 直接译 `244.5`
3. **俄语逗号=小数点**：339,72 → 339.72；Ф1/4 = 1/4 英寸
4. **СБ / ч. / шт 缩写**：СБ=装配件（品名尾部）、ч.=件号、шт=件
5. **乌克兰语按俄语词根翻译**：Найменування→наименование→名称，Кіл-ть→количество→数量

## 异常路径（v1.1 新增）

| 异常 | 处理 |
|---|---|
| rus.traineddata 缺失 | 仅用 eng（俄语变拉丁转写），verify_list 提示"需人工校"；补装：下载到 tessdata 目录（GitHub codeload 可直连，raw/CDN 不通） |

| 微信传输 TIFF 命名混乱 | 常见 `img_t{timestamp}_n1 (1)_01.tif`，按内容识别不按文件名 |

## Pitfalls

- **短数字替换必须限定范围（26BY009 实测踩坑）**：全局字符串替换 "80"→x 会误伤合同号 `100000000000380622`（含 "80"）→ 箱单合同号被改成 `1000000000003[待补充]622`。铁律：**段落只做完整词替换**（日期/规格书号等长词），**数值列只做表格单元格整值匹配**（`cell.text.strip() == 目标值` 才替换）
- **模板表格行结构以 XML 为准，勿信 python-docx 视图**：26BY008 箱单模板 R1+R2 是**两行相同商品**（250+250=500，Total R3 合计），且存在 gridSpan 跨列合并 → row.cells 视图错位（R2C0 与 R3C1 返回同一 tc）。改表格必须 XML 层：`tbl.findall(w:tr)` → `tr.findall(w:tc)`；w:t 嵌套在 w:p/w:r 下，读写用 `tc.iter(w:t)` 而非 `findall`（findall 只找直接子元素会漏）
- **单商品订单清空多余商品行**：模板商品行 >1 时，新订单只保留一行商品，其余行清空（保留格式），Total 行（R3）独立填写合计——勿把 Total 行当第二商品行
- **xlutils.copy 的 write 默认样式覆盖原格式**：不传 style 写入会把单元格变成 Arial/左对齐/无边框/无换行（报关单"排版字体混乱"）。必须用 `xls_tpl.xf_to_style(rb, xf_index)` 从 xlrd XF 构造 xlwt XFStyle（保留字体/对齐/边框/数字格式/换行），`write_cells(wbw, 0, cells, rb=rb)` 传入
- **xls 列位以 dump 为准**：报关单商品行单价在 C8、总价在 C9（0 基，模板 11 列 C0-C10），sample-formats.md 只列值不标列号——首次用模板前必须 `xls_tpl.py dump` 核对列位再写
- **单格混排必须重算对齐空格（26BY009 实测踩坑）**：发票 R7C1 商品行是「品名+数量+单价+金额」单格混排、空格推到固定列位。只替换数字不重算空格 → 数字与表头错位。**用户定稿规则见 A4.5**（品名+数字同行，数量@45/￥@56/单价@57/￥@67/金额@68+）；同样警惕 w:t 级替换对跨 run 文本（日期 '21'+'.0'+'7'+'.2026'）无效，必须段落级合并替换
- **扫描合同 0 字符**：pymupdf `get_text()` 为空 = 扫描件，必须渲染 + OCR，别硬读；OCR 后人工校对全部数字
- **OCR 数字噪声**：长数字（如 100000000000380622）极易错位；俄语逗号是小数点（339,72 = 339.72，106,00 = 106.00）
- **合同号位数不固定**：NLMK 样例为 18 位（旧版误标 19 位导致 `\d{19}` 匹配失败），校验按 16-20 位宽松处理
- **乌克兰语 ≠ 俄语**：用 i/ї/є 字符与 Найменування/Кіл-ть 判断；品名翻译按俄语词根处理
- **.xls 旧格式**：xlrd 只能读；写/改必须 xlwt / xlutils.copy（openpyxl 不支持 .xls）；一律用 scripts/xls_tpl.py
- **模板里的公司名**：模板可能是其他公司（如 Shenyang BYO）的，生成时必须替换为合同中实际供应商/买家，仅保留格式
- **中文路径 + tesseract**：必须 `--tessdata-dir`；TESSDATA_PREFIX 在中文用户名下乱码（脚本已内置）
- **pymupdf 不认 MSYS 路径**：Windows 原生库只接受 `C:/...` 或 `C:\...`，脚本传参用 Windows 路径（实测踩坑）
- **docx 合并单元格**：python-docx 读取合并单元格会重复显示同一值，写入时注意保持合并关系（dump_template 已做相邻去重）
- **docx 空白字符陷阱**：公司名常用不换行空格 `\xa0`，字符串 `in` 匹配误报失败 → validate_3docs.py 已内置归一化
- **单价不得编造**：询价表单价/总价留空；报关单缺失字段（HS 编码、信用代码、毛净重）标 `[待补充]` 列问题清单问用户
- **询价表禁止自创列结构（483165 实测踩坑）**：曾输出 8 列自创表（序号/物料编码/物料全称及规格/单位/数量/参考单价/小计金额/备注）+ 标题行 + 报价要求区，与模板 9 列（Lot/Receiver/俄语名/中文翻译/数量/单重/单价/总价/工期）完全不符，用户要求重做。生成前先 `xls_tpl.py dump` 模板核对列位
- **合计数量必须程序化求和（483165 实测踩坑）**：合计行曾写 76，13 行实际 Σ=130（65 误算 11）。生成后回读文件 Σ 数量列对比合计行
- **单重/Receiver 是独立列，勿"美化"进文本**：单重嵌进规格描述、Receiver 只写进标题区，都会破坏工厂报价可用性
- **execute_code 环境陷阱**：execute_code 与 terminal 的 Python 不同，装库后要写脚本 + `.venv-skill/Scripts/python.exe script.py` 执行
- **中文 Windows heredoc/stdin 陷阱**：git-bash 里 `python - <<EOF` 传 UTF-8 中文脚本，stdin 按 GBK 解码会乱码 → 中文路径 FileNotFoundError。必须 write_file 写 UTF-8 脚本文件再执行；`python -c` 内嵌中文同理，用 Windows 风格路径 `C:/...`（MSYS 的 `/c/...` 原生 Python 不认）
- **PIL decompression bomb**：超大片幅 JPG/GIF（如 11MB、1.8 亿像素的 300dpi 扫描件）触发 `Image.MAX_IMAGE_PIXELS` 报错，脚本开头 `Image.MAX_IMAGE_PIXELS = None`；GIF 多帧时取面积最大帧
- **表格式系列图纸单重**：标题栏 Масса 留空时查图纸内尺寸表（含 Масса 列）按规格行取值；标准表外的定制规格沿用客户清单值并标 `[待核]`，禁止按近似规格推算
- **批量 OCR 重命名幂等**：重命名脚本跑两遍会双后缀（`__name__name`）。目标已存在则跳过；加后缀前先剥已有 `__` 段
- **winget 装 Tesseract 超时**：`winget install --id Tesseract-OCR.Tesseract` 下载 ~50MB，terminal timeout 设 ≥180s；成功前无进度条属正常
- **"按样本格式生成"但找不到样本**：样本可能是 `报价单/` 里的 xlsx 或 `矿山样册/` 里的 PDF，用 `search_files(pattern="*.xlsx")` / `*样本*` 广搜；真找不到再问用户
- **图纸方向旋转**：扫描图可能横竖颠倒，OCR.space 开 `detectOrientation: True`；tesseract 下先旋转校正再 OCR
- **输出格式对应 = 结构对应**：用户说"格式完全对应模板"指列结构/表头/双语布局一致，字体颜色等视觉细节不强制逐像素
