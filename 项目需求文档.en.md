## ⚠️ Core Constraint: Full Windows & macOS Compatibility

> **This project must run normally on both Windows and macOS. All feature designs, code implementations, and path handling must consider both platforms simultaneously.**

| Constraint | Requirement |
|-----------|------------|
| **Path Handling** | Use `pathlib.Path` uniformly. Hardcoding `/` or `\` is prohibited |
| **File Naming** | Use lowercase + hyphens (slug) uniformly. Windows reserved characters `<>:"/\|?*` are prohibited |
| **Directory Depth** | ≤ 3 levels, ensure no violation of Windows MAX_PATH (260 character) limit |
| **Case Sensitivity** | Windows is case-insensitive. File names must be uniformly lowercase to avoid conflicts |
| **Newlines** | Use `utf-8` + `newline=''` when reading/writing text files (Python handles `\r\n` automatically) |
| **Shell Commands** | Do not concatenate shell commands directly in code. Hermes bundles MinGit on Windows |
| **Environment Variables** | Use `TRADE_HOME` (macOS: `~/.trade/`, Windows: `%LOCALAPPDATA%\trade\`) |
| **Installation** | macOS via `curl ... | bash` (same as Hermes), Windows via PowerShell script |

**Hermes upstream Windows support status** (as of May 2026 Hermes README):
- Windows native is **Early Beta**, with a one-click PowerShell install script
- Install path: `%LOCALAPPDATA%\hermes\`
- Bundles MinGit (portable Git Bash) for shell command execution
- WSL2 path is identical to Linux (`~/.hermes/`), the most "battle-tested" Windows approach

**This project's stance on Windows**:
- Goal: Full feature parity with macOS
- Minimum requirement: Windows 10 and above
- Terminal: PowerShell 5.1+ or Hermes-bundled MinGit Bash
- Filesystem: NTFS (default) or ReFS

## I. Project Positioning

**AI sales assistant for foreign trade companies.** Not a simple document Q&A tool, but an intelligent sales system covering the entire "lead generation → conversion" chain.

Traditional foreign trade companies face two core problems:
1. **Lead generation (finding customers)**: How to find more potential customers?
2. **Conversion (securing orders)**: How to turn potential customers into actual orders?

Smart Trade AI trains the Hermes Agent to learn the thinking patterns and business skills of top salespeople, helping foreign trade sales staff improve efficiency in both lead generation and conversion.

**Core Architecture**: Agent Loop — The LLM autonomously decides what files to read, what information to search, and what content to generate, iterating over multiple rounds until the task is complete.

## ⚠️ Core Constraint: Code Architecture (High Cohesion, Low Coupling)

> Business logic must be split. Single scripts/modules must not be too long. Modules should have high internal cohesion and low coupling between modules.
> Added 2026-05-12.

### Rules Overview

| | Rule | Description |
|---|------|-------------|
| **Single Responsibility** | Each module (`.py` file) handles only one thing |
| **File Line Count Limit** | Single `.py` file ≤ 500 lines; must be split if exceeded |
| **No God Modules** | `utils.py` and `helpers.py` must not accumulate unrelated functions |
| **No Reverse Hierarchical Calls** | Upper-level modules can call lower-level ones; lower-level modules must not reference upper-level ones |
| **Dependency Direction = Call Direction** | If module A imports module B, B must not circularly import A |

### Module Layered Architecture

```
trade/                          # Business layer (topmost, calls all lower layers)
├── api.py                      # HTTP routes (≤ 800 lines), request parsing + response assembly only
├── helpers.py                  # Thin glue functions shared across modules (config parsing, prompt construction)
├── prompt.py                   # System prompt templates (pure data)
│
├── company.py                  # Company entity (single responsibility: company CRUD)
├── library.py                  # Document library entity (single responsibility: library CRUD)
├── customer.py                 # Customer entity (single responsibility: customer CRUD)
├── chat_memory.py              # Chat memory (single responsibility: conversation CRUD)
│
└── database.py                 # Data access layer (single responsibility: DB connection + schema + migration)
```

**Layer Description**:

| Layer | Module | Responsibility | Can Call |
|-------|--------|---------------|----------|
| L1 (Entry) | `api.py` | HTTP parsing, response, SSE streaming | L2 |
| L2 (Business) | `company`/`library`/`customer`/`chat_memory` | Business entity CRUD | L3 |
| L3 (Data) | `database.py` | DB connection, schema, migration | None (pure utility) |
| L4 (Data) | `helpers.py` / `prompt.py` | Config parsing, prompt templates | L3 (helpers only) |

### Split Trigger Conditions

When a module meets any of the following conditions, **it must be split immediately**:

```
1. Total lines > 500
2. Responsibility types > 1 (excluding pure data structures)
3. Import chains unrelated to the current module exist
4. Testing requires mocking more than 3 external dependencies
```

### Split Operation Guidelines

**Problematic Module** → **Split Steps**:

```
1. Identify all responsibilities handled by the module
2. Split into independent .py files by responsibility (single responsibility)
3. Place new modules at the same or next layer (dependency direction downward)
4. Demote the original module to a thin forwarding layer (import + re-export only)
5. Ensure no circular dependencies
```

**Example**: If `chat_memory.py` grows to 600 lines, handling both conversation CRUD and hindsight calls:

```
chat_memory.py (600 lines)
    ├── chat_memory.py          # conversation CRUD (demoted to thin layer, ≤ 100 lines)
    └── memory.py                # Hindsight client wrapper (new L2 module)
```

### Prohibited Patterns

```
❌ utils.py (universal toolbox accumulating unrelated functions)
❌ helpers.py exceeding 200 lines
❌ api.py containing business logic (DB operations, entity validation)
❌ L3 modules (lower layer of L2) importing L2 modules
❌ Cross-layer call chain: api.py → database.py → api.py (circular)
```

### Code Comment Standards

> Code must contain sufficient Chinese annotations so readers can understand intent and logic without reading implementation details.
> Added 2026-05-12.

**All functions must have docstrings**:

```python
def get_library(library_id: int, company_id: int) -> dict | None:
    """Retrieve a document library by ID for the specified company.

    Args:
        library_id: Document library primary key ID
        company_id: Company primary key ID (for data isolation validation)

    Returns:
        Document library dict (containing id/name/root_path/description/created_at);
        Returns None if not found or not belonging to the company.

    Raises:
        No exceptions; all error cases return None.
    """
```

**Complex logic must have line-by-line comments**:

```python
# ❌ Bad: No comments
result = [x for x in items if x.get("active") and x.get("company_id") == cid]

# ✅ Good: Line-by-line comments
active_items = [x for x in items if x.get("active")]      # Step 1: Filter active items
company_items = [x for x in active_items                   # Step 2: Filter by company
                 if x.get("company_id") == cid]
```

**Every if/branch must have an explanation**:

```python
if not agent_identity:
    # No company identity config: use generic system prompt (degrade strategy)
    system_parts = [TRADE_SYSTEM_PROMPT]
else:
    # Inject company identity: company name, product scope, sales style
    system_parts = [TRADE_SYSTEM_PROMPT, "", "## Company Identity Configuration", agent_identity]
```

**Code blocks between sections must be separated by comments**:

```python
# =====================================================================
# Section 1: Health Check (Provider Check → Model Config Check)
# =====================================================================

# =====================================================================
# Section 2: Query Construction (Company Identity → Prompt Assembly → Library Context Injection)
# =====================================================================
```

**Comment Coverage Requirements**:

| | Code Type | Minimum Requirement |
|---|-----------|-------------------|
| Function docstring | All (including private functions) |
| if/branches | Every branch must have an explanation |
| Loops | Complex loops must have inline comments |
| Exception handling | Explain why try/except and the handling strategy after catching |
| API routes | Inline comment explaining business meaning (e.g., `# Company ID required, otherwise data cannot be isolated`) |
| Critical business logic | Comment explaining decision basis and business rules |

## III. Multi-Company Architecture (Multi-Tenancy)

> Each company has independent AI identity, document libraries, customers, and conversation records. Data is completely isolated.
> Added 2026-05-11.

### Architecture Overview

```
companies ──────────── trade_companies
    │                        │
    │ 1:N                    │ 1:1 (each company corresponds to one Trade config record)
    ▼                        ▼
libraries ──────────── conversations
    │
    ▼
customers
```

**Data isolation**: All API endpoints and database queries filter by `company_id`. Cross-company data is completely isolated.

### Database Changes

| | Table | Change | Description |
|---|-------|--------|-------------|
| | `companies` | New | Basic company info (name, slug, contact, is_active) |
| | `trade_companies` | New | Trade-specific config (data_dir, agent_identity_md) |
| | `libraries` | +company_id | FK → companies(id), cascade delete |
| | `customers` | +company_id | FK → companies(id), cascade delete |
| | `conversations` | +company_id | FK → companies(id), cascade delete |

**Spare Columns**: All tables reserve 3 TEXT-type spare columns (`extra1`/`extra2`/`extra3`), default `'{}'`, for storing JSON-structured extension fields, avoiding the need for ALTER TABLE on future schema changes. All 6 tables have a total of 18 spare columns.

| | Table | extra1 | extra2 | extra3 |
|---|-------|--------|--------|--------|
| | `companies` | `{"industry":"","country":""}` | `{"employee_count":"","annual_revenue":""}` | Reserved for future extension |
| | `trade_companies` | `{"max_iterations":90,"temperature":0.7}` | `{"model":"","provider":""}` | Reserved for future extension |
| | `libraries` | `{"scan_depth":3,"file_count":0,"last_scan":""}` | `{"indexed":false,"index_version":1}` | Reserved for future extension |
| | `customers` | `{"country":"","website":"","linkedin_url":""}` | `{"customer_type":"","tier":"","source":""}` | Reserved for future extension |
| | `customer_libraries` | `{"relevance_score":0.0,"notes":""}` | Reserved for future extension | Reserved for future extension |
| | `conversations` | `{"tokens_used":0,"model":"","duration_ms":0}` | `{"rating":null,"feedback":""}` | `{"tools_used":[],"iterations":0}` |

Idempotent supplement mechanism: `_add_spare_columns(conn)` is called once each in `init_db()` and `_migrate_from_v0()`, using `ALTER TABLE ADD COLUMN` (SQLite silently ignores if column already exists), supporting safe repeated execution.

### v0 Migration

## III. Core Business Features

### 3.1 Lead Generation — Finding Customers

#### 3.1.1 B2B Platform Diagnosis & Optimization

Users provide product links from Alibaba International Station / Made-in-China / independent websites. The Agent diagnoses the platform store and provides improvement suggestions:
- Analyze the quality and coverage of product titles, keywords, and descriptions
- Check whether product images and videos comply with platform best practices
- Compare with top competitor stores, identify gaps and optimization directions
- Output directly executable product publishing / modification checklists

**Input**: Platform store link or product link
**Output**: Diagnostic report + improvement plan (title optimization, keyword suggestions, description templates, image requirements)

#### 3.1.2 Social Media Content Strategy & Material Generation

Users provide competitor social media account links (Facebook / Instagram / TikTok / YouTube). The Agent learns the competitor's content strategy and generates a social media publishing plan based on the company's products:
- Analyze competitor content types, publishing frequency, engagement data, and hashtag strategies
- Generate a social media content calendar suitable for the company's products (weekly / monthly plan)
- Provide ready-to-publish specific posts (copy + image suggestions + hashtags)

**Input**: Competitor social media links (multiple allowed) + company product materials
**Output**: Social media publishing plan + content calendar + specific posts (ready to copy-paste and publish)

#### 3.1.3 LinkedIn Marketing Plan

Users provide company product materials. The Agent generates a complete LinkedIn marketing plan using LinkedIn B2B development methods:
- **Customer Profile**: Define target customers based on product characteristics (position, industry, region, company size)
- **Personal Account Setup**: Content templates for profile photo, background image, headline, About section
- **Company Page Setup**: Company introduction, product showcase, employee invitation strategy
- **Annual Marketing Plan**: Includes planned timeline and specific execution content, ready to copy-paste and use
- **Content Material Library**: Template library for industry insight posts, product value posts, customer case posts

**Input**: Company product catalog / specification sheet + industry materials
**Output**: Customer profile + account setup templates + company page content + annual marketing plan (with schedule)

#### 3.1.4 Customs Data / Canton Fair Data Mining

Users upload customs data (import/export records) or Canton Fair exhibitor data. The Agent automatically filters:
- Extract target customers (buyers / importers) in the industry from the data
- Analyze customer purchasing patterns (frequency, quantity, category, season)
- Output prioritized target customer list
- Provide development suggestions for each customer (entry point, recommended products, expected order volume)

**Input**: Customs data file (CSV / Excel) + company product scope
**Output**: Industry target customer list + development priority + development strategy for each customer

#### 3.2.1 AI Senior Salesperson

The Agent trains to become an AI with senior foreign trade salesperson thinking patterns and business skills by learning the following materials:

**Training materials**:
1. Senior salesperson thinking methodology

**Capability requirements**:
- Understand B2B sales psychology and decision-making chains
- Master the full foreign trade process: Inquiry → Quote → Negotiation → Close → Order follow-up
- Adjust communication strategies based on different customer types (price-sensitive / quality-oriented / relationship-oriented)

**Analysis Dimensions**:

**Output Content**:

- Customized outreach email / LinkedIn InMail (ready to copy-paste and send)

**Input**: LinkedIn customer link or customer information text (company name + contact + position)
**Output**: Customer analysis report + outreach email / message + follow-up plan

### 3.11 OSINT Customer Background Check & Risk Assessment (Upgraded Due Diligence)

> Added 2026-05-12. Originates from real needs identified in customer due diligence conversations: single email platform detection is insufficient; multi-signal cross-validation is needed.

#### 3.11.1 Current Status & Gaps

**Current `b2b-email-intel` capabilities**:
- Only detects email registration status on 121+ mainstream platforms (`holehe`)
- Output: Platform name | Registered or not | Username | Profile URL

**Real due diligence needs revealed in conversations** — Complete due diligence requires cross-validation across 5 dimensions:

| Verification Dimension | Current | Target |
|----------------------|---------|--------|
| Email platform registration | ✅ `holehe` | Retain |
| Domain registration info | ❌ Missing | WHOIS lookup (registration date/registrar/expiry date) |
| Corporate email verification | ❌ Missing | `@company.com` vs Gmail/QQ personal email detection |
| Website tech stack | ❌ Missing | BuiltWith detection (WordPress/Shopify/Custom) |
| Sanctions list screening | ❌ Missing | OFAC/UN/EU/China sanctions cross-referencing |

**Core Insight (from conversations)**: A single signal is insufficient; multi-signal cross-validation is needed. For example:
- LinkedIn page looks real, but the domain was registered 3 months ago → Red flag
- Corporate email uses `gmail.com` instead of `@company.com` → Red flag
- Website tech stack is a free blogging platform → Red flag

#### 3.11.2 Multi-Layer Verification Architecture

#### 3.11.4 Risk Scoring System

**Cross-Validation Scorecard** (each item scored independently, aggregated into overall rating):

```
✅ Positive Items                           ⚠️ Negative Items
─────────────────────────────────────────────────────
Domain > 3 years                            Domain < 1 year
Has corporate email (@company.com)          Only uses gmail/qq/163
LinkedIn company page exists with many employees    No LinkedIn company page
Website tech stack is legitimate (enterprise-grade)  Free blog/temporary website builder
Domain age ≈ company founding date          Domain much older than company
WHOIS registration info complete            WHOIS privacy protection/info missing
Not on any sanctions list                   Appears on any sanctions list
```

**Overall Rating Definitions**:

| Rating | Condition | Recommendation |
|--------|-----------|---------------|
| Low Risk | Positive items ≥ 4 and no red flags | Proceed normally |
| Medium Risk | 1-2 red flags | Proceed with caution, request more verification |
| High Risk | Red flags ≥ 3 or hit on any sanctions list | Strongly recommend rejection, or executive approval required |

## VIII. Project History & Lessons Learned

### 8.1 VibeRAG Three Iterations (Deprecated)

| Version | Architecture | Result |
|---------|-------------|--------|
| V0.21 | Pure vector retrieval (ChromaDB + embedding chunk) | Vector matching rate lower than irrelevant documents |
| V2 | Pure FTS + LLM direct file reading | Three AI reviewers objected (semantic recall missing) |
| V3 Improved | FTS primary recall + five auxiliary paths + LLM precise segment reading | Two-week field testing, significant gap compared to Hermes |

### 8.2 Five Fatal Architecture Issues

1. FTS keyword matching missed recall
2. Page-level truncation lost context
3. Table JSON conversion caused information loss
4. Single LLM call had no error correction capability
5. Gap compared to Hermes Agent Agent Loop

### 8.3 Lessons Summary

- The essence of B2B scenarios is Agent Loop + Tool Calling, not a retrieval pipeline
- Forking mature open-source projects as a foundation is more practical than building from scratch
- Do not underestimate the complexity of table parsing and OCR

## 3.12 Prompt Isolation Architecture (User-Editable System/Skill Prompt)

> Added 2026-05-12. All prompts injected into the LLM by the system support user editing, with file priority and DB caching.

### 3.12.1 Architecture Principles

| Principle | Description |
|-----------|-------------|
| **File is Source of Truth** | `.md` files under `~/.trade/` are the authoritative source for prompts |
| **DB is Runtime Cache** | Fields like `agent_identity_md` serve as hot caches for files; file changes take effect automatically |
| **mtime Cache** | Avoids re-reading files on every request; changes to files automatically invalidate and reload the cache |
| **Skill reads from SKILL.md** | `injection_prompt` exists in `SKILL.md` frontmatter; users change behavior by editing the skill file |

### 3.12.2 Prompt File Layout

```
~/.trade/                                  # Runtime data (.gitignore)
├── prompts/
│   └── system.md                         # Global system prompt (user-editable)
├── companies/{slug}/
│   └── agent_identity.md                 # Company-level agent identity (overrides global system)
└── companies.db                          # agent_identity_md field = hot cache

~/.hermes/skills/b2b-osint/
└── SKILL.md                              # injection_prompt in frontmatter
```

### 3.12.3 Read Priority

**System Prompt (vertical override, highest priority wins):**
1. `~/.trade/companies/{slug}/agent_identity.md` — Company-level
2. `~/.trade/prompts/system.md` — Global custom
3. Code fallback (`TRADE_SYSTEM_PROMPT` in `trade/prompt.py`)

**Skill Injection (vertical override, highest priority wins):**
1. `injection_prompt` in `~/.hermes/skills/{skill}/SKILL.md` frontmatter
2. Code fallback (`_SKILLS` dict in `skill_router.py`)

**Final Assembly (horizontal):**
```
system_prompt + skill_injection + doc_context + user_query
```

### 3.12.4 Automatic File Change Detection

`trade/prompts.py` maintains an mtime cache (`_PROMPT_CACHE`):
- File `mtime` unchanged → Use cache directly
- File `mtime` changed → Re-read file, update cache
- User `vim ~/.trade/prompts/system.md` → Next request automatically takes effect, no restart needed

### 3.12.5 Implementation Files

| File | Purpose |
|------|---------|
| `trade/prompts.py` | Unified prompt file loader (mtime cache) |
| `trade/skill_router.py` | Reads `injection_prompt` from SKILL.md frontmatter |
| `trade/helpers.py` | Uses `prompts.resolve_system_prompt()` |
| `trade/onboarding.py` | Dual write to identity file + DB |
| `.trade-template/prompts/system.md` | System prompt installation template |
| `.trade-template/companies/company-slug/agent_identity.md` | Agent identity installation template |


## 3.13 Long-term Conversation Memory & History Query

> Added 2026-05-12. Solves the problem of "not knowing today what was discussed yesterday" — all conversations are permanently stored with timestamps, and the Agent can proactively query at any time.

### 3.13.1 Core Principles

- **All conversations stored permanently**: No compression, no summarization, no deletion. `created_at` is a required field
- **Default recent history injection**: 10-20 rounds (~10k tokens), ensuring recent context coherence
- **Earlier history queried on demand**: Agent proactively queries via tools; LLM determines when to execute based on tool descriptions
- **Thresholds controlled by code**: Completely transparent to users
- **Hermes native memory interop**: `save_with_context()` automatically writes a summary to `~/.hermes/memories/MEMORY.md` after each conversation save; Hermes Agent can remember B2B business conversations across projects

### 3.13.2 Token Budget Allocation

| Segment | Limit | Description |
|---------|-------|-------------|
| System prompt | ~5k | Company identity + doc context |
| Skill injection | ~1k | Currently triggered skill augment |
| **Recent history** | **~10k** | **Fixed 10-20 rounds, most recent context** |
| Current query | ~1k | User's current question |
| Reserved space | ~83k | Reserved for Agent reasoning and response |

### 3.13.3 Prompt Construction Logic (build_query)

**Threshold evaluation target: total token count of the entire prompt**

```python
# Thresholds hardcoded, not exposed to the user
if total_tokens < 20_000:
    history_limit = 20   # Ample space, inject more history
    hint = None
elif total_tokens < 50_000:
    history_limit = 10    # Start compressing history volume
    hint = "For earlier conversation history, please use the chat_memory_list tool."
else:
    history_limit = 5     # Force trimming
    hint = "Current context is long. Conversation history has been trimmed. To query earlier content, please use the chat_memory_list tool."
```

**History injection is always a fixed number of rounds (history_limit), not growing indefinitely with thresholds.**

### 3.13.4 Tool Description Driven (No Trigger Words)

When the Agent queries history is not determined by trigger words, but by tool descriptions:

```json
{
  "name": "chat_memory_list",
  "description": "Query historical conversation records for the current company. When the user mentions time-related words
                 like 'before', 'last time', 'previously', or asks about content discussed in the past,
                 use this tool to retrieve relevant history.",
  "parameters": {
    "time_range": {
      "type": "string",
      "enum": ["today", "this_week", "this_month", "all"],
      "description": "Time range: today/this week/this month/all"
    },
    "limit": {
      "type": "integer",
      "default": 20,
      "description": "Maximum number of messages to return"
    }
  }
}
```

The LLM reads the tool description from SKILL.md and decides when to call it — when the user says "what was the name of that supplier you recommended last time", the LLM will proactively query `chat_memory_list`.

### 3.13.5 Division of Labor: Hindsight vs SQLite

| Query Type | Example | Storage / Retrieval |
|-----------|---------|-------------------|
| **Time-series query** | "Yesterday's conversation", "What was discussed last week" | SQLite `ORDER BY created_at` |
| **Semantic query** | "That chip supplier", "The plan mentioned earlier" | Hindsight vector retrieval |

- Has Hindsight API Key → Time-series via SQLite, semantic via Hindsight
- No Hindsight API Key → Semantic queries degrade to SQLite `WHERE query LIKE '%keyword%'`

### 3.13.6 Implementation Plan

| Priority | Content | File |
|----------|---------|------|
| ~~P0 ✅~~ | `build_query()` injects recent 10-20 rounds of history + token threshold hint | `helpers.py` |
| ~~P0 ✅~~ | `chat-memory` skill: SKILL.md + tool description (no trigger words) | `skills/chat-memory/` |
| ~~P0 ✅~~ | `chat_memory_list(time_range, limit)` function | `chat_memory.py` |

## XII. Upgrade Logic (Data Integrity Protection)

> When Trade is upgraded, existing business data (database, company directory files) must remain intact and usable.
> No user data may be lost due to schema changes. Added 2026-05-12.

### 12.1 Design Principles

| Principle | Description |
|-----------|-------------|
| **Backward Compatibility** | New version code must be able to read and write data created by old versions |
| **Automatic Migration** | Detect and execute migration automatically on startup, no manual user intervention required |
| **Atomicity** | Database rolls back on migration failure, leaving no half-finished state |
| **Idempotency** | Migration scripts can be safely re-executed without duplicating data |
| **Reversibility** | Migration scripts have clear `up()` / `down()` logic (implemented in Python, not SQL comments) |

### 12.2 Migration Detection Mechanism

Each time `init_db()` executes, the database layer checks the current schema version in the following order:

```
1. Read PRAGMA table_info(libraries) — get current column set
2. Determine whether the "company_id" column exists
   ├─ Does not exist → v0 schema (single-company version)
   └─ Exists → v1 schema (multi-company version)
3. Subsequent version detection follows the same pattern, progressing version by version
```

**Important**: Does not use a separate `schema_version` table. Instead, detects the version by checking whether key columns exist.
Reason: Avoids atomicity risks from multi-table writes; the column's existence proves that version's migration is complete.

### 12.3 Version Evolution & Migration Paths

#### v0 → v1: Single Company → Multi-Company (Multi-Tenancy)

**Trigger Condition**: Detected that the `libraries` table has no `company_id` column.

**Data State Before Migration** (v0):
```
libraries:     id, name, root_path, description, created_at, updated_at
customers:     id, name, contact, note, created_at, updated_at
conversations: id, query, response, files_read, created_at
```

**Data State After Migration** (v1):
```
companies:        id, name, slug, logo_url, website, contact_name, ...,
                 extra1='{}', extra2='{}', extra3='{}'
trade_companies: company_id(PK), data_dir, agent_identity_md, is_active, created_at,
                 extra1='{}', extra2='{}', extra3='{}'
libraries:       + company_id (FK → companies(id), DEFAULT 1),
                 extra1='{}', extra2='{}', extra3='{}'
customers:       + company_id (FK → companies(id), DEFAULT 1),
                 extra1='{}', extra2='{}', extra3='{}'
conversations:   + company_id (FK → companies(id), DEFAULT 1),
                 extra1='{}', extra2='{}', extra3='{}'
```

**Migration Operation Steps** (`database.py:_migrate_from_v0()`):

```
Step 1: Create new tables
  CREATE TABLE companies (...)
  CREATE TABLE trade_companies (...)
  INSERT OR IGNORE INTO companies (name='My Company', slug='default', ...)
  INSERT OR IGNORE INTO trade_companies (company_id=1, data_dir='', ...)

Step 2: ALTER TABLE (add columns per table)
  ALTER TABLE libraries     ADD COLUMN company_id INTEGER REFERENCES companies(id) ON DELETE CASCADE
  ALTER TABLE customers     ADD COLUMN company_id INTEGER REFERENCES companies(id) ON DELETE CASCADE
  ALTER TABLE conversations ADD COLUMN company_id INTEGER REFERENCES companies(id) ON DELETE CASCADE

Step 3: Fill company_id (all existing data belongs to company 1)
  UPDATE libraries    SET company_id = 1
  UPDATE customers    SET company_id = 1
  UPDATE conversations SET company_id = 1

Step 4: Create indexes
  CREATE INDEX idx_libraries_company     ON libraries(company_id)
  CREATE INDEX idx_customers_company     ON customers(company_id)
  CREATE INDEX idx_conversations_company ON conversations(company_id)

Step 5: Add spare columns (all 6 tables)
  _add_spare_columns(conn)  # Idempotent ADD COLUMN, silently ignores if column exists
```

**Data Integrity Guarantees**:
- All existing data automatically belongs to company 1 ("My Company"), no records lost
- New tables and old table data are completed in the same transaction; failure rolls back everything
- `ON DELETE CASCADE` ensures deleting a company automatically cleans up all its business data

---

#### v1 → v2 (Example, Future Extension)

Every future schema change follows the same pattern, appending a new `_migrate_v1_to_v2()` function in `database.py`:

```python
def _migrate_v1_to_v2(conn):
    # Step 1: Check if migration is needed (idempotency)
    cur = conn.execute("PRAGMA table_info(libraries)")
    cols = {row[1] for row in cur.fetchall()}
    if "new_column" in cols:
        return False  # Already migrated

    # Step 2: Execute migration (within the same transaction)
    conn.execute("ALTER TABLE libraries ADD COLUMN new_column TEXT DEFAULT ''")
    # ... other operations

    # Step 3: Add spare columns (required for every new table in the future)
    _add_spare_columns(conn)

    conn.commit()
    return True
```

### 12.4 Directory File Migration

Company data directory (`~/.trade/{slug}/`) migration is handled in `company.py:_ensure_data_dir()`:

```
Trigger timing: Called during company.create() or company.get()
Trigger condition: Target directory ~/.trade/{slug}/ does not exist

Migration operation:
  1. Read .trade-template/ as source
  2. Copy template to temporary directory
  3. Rename placeholder directories:
       companies/company-slug  → companies/{slug}
       libraries/library-slug  → libraries/{slug}
       clients/client-slug     → clients/{slug}
  4. Move temporary directory → ~/.trade/{slug}/
```

**Data Integrity Guarantees**:
- `if target.exists(): return target` — Existing company directories are never overwritten
- New companies use the template for creation, not affecting existing company directory files
- `shutil.move()` is an atomic operation (within the same filesystem)

### 12.5 Upgrade Failure Handling

| Failure Scenario | Handling Method |
|-----------------|-----------------|
| Database migration SQL execution failure | `conn.rollback()` rollback, process exits with error message |
| Company directory creation failure | `company.create()` throws exception, DB transaction not committed |
| Template directory does not exist | `_ensure_data_dir()` silently creates empty directory, does not block company creation |
| Insufficient disk space | Python IOError, process exits, DB not written |

**Log Output**:
- Migration start: `Detected v0 schema — migrating to multi-company v1 ...`
- Migration complete: `Migration complete. Default company 'My Company' (slug=default) created.`
- Migration failure: Complete SQLite error message for diagnostic purposes

### 12.6 Version Downgrade

Trade **does not support** downgrading from a higher version to a lower version. Downgrade requires manual user action:
1. Back up the `~/.trade/` directory and `data/trade.db`
2. Reinstall the old pip package
3. Manually restore data

Downgrade protection rationale: ALTER TABLE is irreversible (SQLite does not support DROP COLUMN), downgrading could lead to data loss.

### 12.7 Pre-Upgrade Checklist (For Maintainers)

Before releasing any new schema change, confirm:

```
[ ] New migration function implements up() logic, idempotency verified
[ ] Execute migration on old-version database, all existing data preserved
[ ] Rollback new-version database to pre-migration state, verify rollback works
[ ] Company directory structure correct after migration (companies/{slug}/ etc. renamed)
[ ] Frontend correctly accesses migrated company data (X-Company-ID routing works)
[ ] Unit tests cover the migration path (test_v0_to_v1_migration)
```
