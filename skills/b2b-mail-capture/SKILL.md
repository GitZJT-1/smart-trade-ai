# B2B 询价/招标邮件批量抓取与归档（通用模板）

> 本版为跨设备通用版：路径、账号、项目编号均已参数化/匿名化，配置即可用。

## 环境要求与配置

- Python stdlib 即可（`imaplib`/`ssl`/`email`/`json`），无第三方依赖。
- 凭据配置：复制 `scripts/mail_accounts.example.json` 为 `scripts/mail_accounts.json`，填入邮箱、`imap_host`/`imap_port` 与 IMAP 授权码（`auth_code` 为空的账号会被跳过并明确列出，不要假装抓了）。
- 落盘根目录优先级：环境变量 `MAIL_CAPTURE_DIR` > `mail_accounts.json` 的 `output_dir` > `mail_lib.py` 默认值（`~/Desktop/邮件抓取结果`）。
- **agent 运行账户 ≠ 桌面用户时**（如 Windows 服务/SYSTEM 会话）：`os.path.expanduser("~")` 会解析到运行账户的 profile，**不是**用户的真实桌面——落盘根目录必须显式配置（环境变量或 json），不要用 `~`。曾踩坑：脚本把结果写到了错误账户的桌面。

## 用途

把某个邮箱**时间窗口内**的邮件拉下来，按「询价」/「招标」分类，下载业务附件，按**日期_主题**逐封落盘归档。适合定时监控之外的补抓、或按要求回看近几天邮件的场景。

> 关系：**本文档负责「抓取→分类→下载→按天归档」这段**。抓下来的附件再加工成询价单/结构化报价，走 `b2b-tender-processing`。本文档的产物即它 Step 1 需要的 `0.PDF`/附件源。

> 下游解析笔记：SRM 主 PDF（`0.PDF`）的字段位置、行项表**文本顺序错乱**的判定规则、采购方备注必摘条款、附件核对法，见 `references/nlmk-srm-main-pdf-notes.md`（以 NLMK SRM 为实例，其他 SRM 平台可参照）。

> 招标文件夹整理（行项取哪个源、进度表结构、压缩包解压命名、截止时间提取、备注里的商务条款）见 `references/nlmk-tender-folder-organization.md`。

## 落盘约定（产物形态）

- **按天归档**：结果放到 `BASE/<邮件日期 YYYY-MM-DD>/`，每天一个子目录，历史批次不被后覆盖。
- **按「日期_主题」命名**：每个邮件落成 `<YYYY-MM-DD>_<主题>.txt`（抓取账号/发件人/时间/主题/附件都写进文件内容）。同一天同主题冲突时末尾追加 `_<uid>` 去重。
- **附件落盘**：`<BASE>/<YYYY-MM-DD>/<YYYY-MM-DD>_<主题>_附件/`，与同邮件的 `.txt` 同名并列，便于对照；`.txt` 末尾补一行 `附件目录: <绝对路径>（已下载 N 个文件）`。
- ⚠️ **磁盘上的实际目录名不含「（已下载 N 个文件）」后缀**——那个后缀只存在于 `.txt` 的字符串里。照抄字符串去 `ls`/`cp` 会 `No such file`；拼路径时把括号连同后缀去掉。
- **不生成 xlsx 清单**（推荐约定，可按需改）：邮件子目录树本身就是索引。禁止回到「单一 `*_邮件.txt` 覆盖写」的老做法——那会把当天多批次新邮件只留下最近一次快照。

## 脚本

- `scripts/mail_lib.py` — 共享库：账号/断点加载、IMAP 连接、噪音过滤、附件下载、按天归档落盘（`save_email_results`）、增量抓取（`run_for`，可作定时任务直接跑）。
- `scripts/fetch_inquire_tender.py` — 近 N 天询价/招标窗口补抓（`DAYS_BACK` 可调；`MAIL_ACCOUNT` 环境变量指定账号，默认取 json 里第一个有授权码的）。
- `scripts/backfill_attachments.py` — 补抓历史邮件附件：按已有 `.txt` 的「日期_主题」命名从 IMAP 重取信、落附件、补「附件目录」行。
  ```bash
  python backfill_attachments.py 01-Sep-2026
  ```

## 分类关键词（俄/英）

- **询价**：`запрос` / `к[пп]`(КП=коммерческое предложение) / `цен[аыу]` / `quote` / `inquiry` / `опрос` / `thermo`
- **招标**：`конкурс` / `тендер` / `закупк[аи]` / `запрос предлож` / `зп-` / `сп.` / `п[аа]о ... н[лмк]`(ПАО+厂名) / `закуп`
- 优先匹配询价特征，再判招标；两者都命中时按「招标」归（如 `ПАО <厂名>-ЗП-...` 这种厂家项目号）。
- 常见业务形态：`Fw:Конкурс <8位编号>/<版本>` 是招标；`RE: Запрос КП / Запрос цены` 是询价。

## 附件处理规则

- 只下载 `part.get_filename()` 非空的附件，`get_payload(decode=True)` 写二进制。
- **剔除内联签名图**：`image00\d\.(png|jpg|jpeg)$` 是正文装饰图/logo，不是附件，跳过；inline 且 <60KB 的图片同样跳过。
- 同名附件自动加 `(2)`、`(3)` 序号，不覆盖。
- 不要把 `.eml` 当附件整理进去（它留在抓取源）。

## 用户只报标段号时：一步定位源目录

用户常只丢一串标段号（如 `20157145/0 20157168/0`）说「这几个标段需要整理询价文件」，不给路径。流程：

1. **标段号就在转发主题里**（`Fw:Конкурс 20157145/0`）——对邮件抓取结果整棵树做**一次按标号的内容检索**，一次拿齐全部源目录与日期（常跨多个日期目录，一次检索全部命中，不用逐日翻）。
2. 先 `ls -d <交付根目录>/*<标段号>*` 确认本地没有既有的整理文件夹，再动手（查重思路同 `b2b-tender-processing`）。
3. 源目录形如 `邮件抓取结果/<YYYY-MM-DD>/<YYYY-MM-DD>_Fw_Конкурс <标号>_0_附件/`，同一标段跨多日重复出现时取**最新日期**目录（附件最全）。

## 多标段一次整理

一次丢多个标段号时：

1. 对抓取结果整棵树做**一次**按标号的内容检索即可全部命中，不用逐日翻。
2. ⚠️ **同一标段可能到达两封，附件分散**：第一封只带 `0.PDF`，第二封带全部图纸附件，落成 `<主题>_0_<UID>.txt` 与 `..._<UID>_附件/`。整理时**以附件多的那封为准**，但两封的附件目录都要看——只取先到的那封会漏掉全部图纸。目录名带 `_<数字>` 后缀就是在提示这是重复到达件。
3. 动手前先查重；整理完成后校验源目录文件数未变。
4. 多个标段用**同一个 `{YYMMDD}-` 前缀**（取生成当天），交付报告列全完整文件夹名，不要只报「已整理完」。
5. 交付报告必须带**截止时间 + 到期状态**，已过期的单独点名、当天到期的排最前——见 `references/nlmk-tender-folder-organization.md`。

## 交付物核对与「少文件夹」申诉（先盘面，再补做）

用户会说「只有五个文件夹，还有两个你没生成」。**先核验，禁止直接重做**——重建会产生重复文件夹、覆盖已完成的询价单，而且往往结论是「其实一个都不缺」。

1. **盘点存量**：`ls -d <交付根目录>/<前缀>*`，再逐个 `ls` 看 `0.PDF` + 编号附件 + `{标段}{品名}等询价单.xlsx` 是否齐全（`stat` 看创建/修改时间，判断是不是同一批落盘）。
2. **前缀 = 出单当天日期（推荐约定）**：`{YYMMDD}-{标段}{品名}-{状态}` 里的日期取**生成当天**，同一次整理出的所有标段必须**同一个**前缀。历史教训：一次整理 7 个标段时按邮件到达日命名，桌面按名排序后两组不相邻（旧前缀夹在更早的文件夹里），扫一眼只看见连排的 5 个就报「少了两个」。**同批同品名冲突时用标段号区分，不要回退到邮件到达日。**
3. **交付报告一律列完整文件夹名**（含日期前缀）；存量文件夹前缀混用时**主动批量归拢成当天前缀**，改完按文件数回读核对。中途报 `Device or resource busy` 的目录**不是权限问题**：常是早前某进程的 CWD 停在那（Windows 用 handle64/资源监视器定位 pid 后结束，Linux 用 `lsof`），锁释放后重发即成功；已成功的不要回滚。
4. **交叉核对数量**：邮件源附件目录的附件数 vs 交付文件夹内编号附件数。
5. **复核上一轮到底承诺了什么**：上下文里的历史回答常被截断，去权威记录（会话历史/应用数据库）取最近几条完整交付清单再比对。
6. 确认磁盘上确实没有、或内容不全时才补做；**只补缺的那几条，就地补齐不重建整批**。另可顺带提醒尚未建文件夹的新到标段。

## 铁律

1. **落盘根目录显式配置**：agent 运行账户可能与桌面用户不同，`~` 会解析错（见「环境要求」）。
2. **分类明细 + 落盘回读验证**：跑完列目录树 + 核对每个邮件子目录是否真实存在，交付报告务必给出数据（询价 X 封 / 招标 Y 封 / 附件 Z 个 / 文件路径），不要只报「已抓完」。
3. **账号授权码**：`auth_code` 为空的账号会被跳过——先查 json 确认哪些账号真能抓，抓不到的明确列出来让用户去补码，不要假装抓了。
4. **输出形态**：结果文件**按天归档**（`BASE/<YYYY-MM-DD>/`）＋**按「日期_主题」逐封命名**，禁止覆盖式单文件写法。

## 陷阱

- **「有附件」≠「附件已落盘」**：`.txt` 里的「附件:」行只是收件时抄下的文件名。判断附件是否真在，要看同级有没有 `*_附件/` 目录；批量核对用脚本遍历 `.txt` 的「附件:」行与同级目录，别只看文件名列表就报「附件已抓」。
- 补抓时**未匹配到已有 `.txt` 的邮件要如实列出**（通常是采集开始日之前的邮件，或未归档的日期目录），不要为了凑数给它们新建目录。
- 记得清掉误写进错位置的测试产物。
- `SEARCH SINCE %d-%b-%Y` 用 `01-Sep-2026` 这种格式才认；增量抓取受 `last_uid` 限制，要干净窗口就绕过它直接按日期搜。
- 分类可能把转发的同一条线程抓多封（`Fw:Re:Fw:` 不同 UID 同一标书），保留每行即可，不要合并去重成一条——每封是独立到达的邮件。
- **系统通知邮件黑名单**：`mail_lib.is_noise()` 内置发件人/主题黑名单（noreply/postmaster/bounce/验证码/异地登录/退信/spam 等），命中即**不落盘**且记入断点——这是故意跳过，不是漏抓，排查缺邮件时先按发件人/主题判断是否命中黑名单。
