# 批量解压与归档清理（7z）

## 触发场景
- 用户有一批压缩包（.7z/.rar/.zip/.gz）需要解压到**各自所在目录**（原文件对应地址），完成后**删除原压缩包到回收站**释放空间
- 压缩包是俄文图纸数据（招标下载产物），常见"包中包"多层嵌套
- 典型路径：`...\\报价单\\КФ_解压` / `БФ_解压` 下按 kf_*/bf_* 分类存放，或 `...\\报价单\\周家同\\<项目号>归档`
- **解压后常需后续处理**：将非纯数字文件夹名统一改为纯数字编号（如 `1007-Ролик...` → `1007`），冲突时合并——详见 `references/post-extraction-renaming.md`
- **解压后常需完整归档流程**：将平放文件按编号前缀归入对应数字文件夹、处理非标准命名文件、按零件名归组——详见 `references/complete-archiving-workflow.md`

## 核心流程
1. **统计摸底**（先只读不动作）：遍历所有压缩包（.7z/.rar/.zip/.gz），输出总数 / 总大小 / 0字节损坏数
   - 不要只搜 .7z——招标归档中 .rar 和 .zip 同样常见，7z CLI 均可处理
2. **第一轮解压**：对每个包 `7z x -y -o<所在目录> -- <包路径>`，rc 0/1 视为成功 → **立即删除原包到回收站**
   - 删除方式：PowerShell `Add-Type -AssemblyName Microsoft.VisualBasic; [Microsoft.VisualBasic.FileIO.FileSystem]::DeleteFile("<路径>", "OnlyErrorDialogs", "SendToRecycleBin")`
   - ⚠️ 用回收站而非永久删除——万一解压产物有问题，可从回收站恢复原包重试
3. **嵌套迭代**：解压后**重新全目录扫描**（含子目录），若仍有压缩包（包中包）→ 继续解压删除，直到 0 残留
   - 真实案例 A：559 个顶层包 → 解压后又发现 80 个嵌套包 → 共 628 个全部处理完、0 残留
   - 真实案例 B：28 个顶层包 → 解压后在子目录发现 49 个嵌套包 → 第二轮全部清零
   - 最多 15 轮防死循环（同名自嵌套场景）
4. **删除重试**：删除失败（WinError 32 文件被占用，多为杀毒软件实时扫描）→ 等 ~20s 重试，一般首轮即成功
5. **最终验证**：全目录扫描 0 个压缩包残留 + 统计解压产物文件数/总大小（交付物为准）
6. **编号归组（可选后续步骤）**：若解压后需按图纸编号归组，参见 `references/post-extraction-renaming.md`

## ⚠️ 操作前安全核查（必须，2026-08-05 事故教训）
目录可能被后台进程并发修改（Trade AI 下载任务 server.py、Hermes cron、用户其他工具），批量解压/改名/清理进行中目录被整体删除会导致数据丢失且操作白做。执行任何批量文件操作前：
1. **稳定性快照**：间隔 10-15s 两次全量 `os.walk` 统计条目数，数量不一致 → 有进程在动，先排查再动手
2. **进程排查**：PowerShell `Get-CimInstance Win32_Process` 查所有 python/7z 进程命令行；psutil 查父子链与 CPU 时间——高 CPU 的挂起 server 类进程是嫌疑（launcher 0 CPU 但 spawn 了干活子进程）
3. **回收站验证**：COM `(New-Object -ComObject Shell.Application).Namespace(0xA)` 条目数——程序化 rmtree 删除不进回收站，无法恢复
4. **cron 排查**：`%LOCALAPPDATA%\hermes\cron\jobs.json` 查看有无清理/下载类定时任务及其最近执行时间
5. **操作中监控**：处理期间若发现条目数骤降/目录消失，立即中止写入、先汇报用户再继续

## 坑与要点
- **7z 路径**：`/c/Program Files/7-Zip/7z.exe`（Windows 标准安装位）
- **返回码语义**：0=成功；1=警告（如无法设时间戳）**也算成功**；2+=致命错误保留原包；超时记 99
- **完整性**：`7z t <包>` rc=0 有效；**0 字节包跳过**（损坏）
- **俄文乱码文件名**：包内俄文名可能解压成乱码——**可逆，不要放弃改名**。成因：CP866 字节流被按 GBK/CP936 解码（汉字=2 字节配对、单字节→Latin-1 补充字符、PUA 扩展映射、€=0x80）。**首选方案**：Windows API `WideCharToMultiByte(CP_GBK=936)` 一站式还原（含高位 PUA，2026-08-12 实测 51/51 全量修复）。备选方案：残留 zip 包内部条目名 `filename.encode('cp437').decode('cp866')` 即正确俄文名，按"结构对齐 + ASCII 骨架匹配"对应到磁盘乱码条目。完整算法与验证见 `references/mojibake-reverse-engineering.md`
- **同名自嵌套**：如 `Тележка.7z` → `Тележка\\Тележка.7z` 三层同名嵌套，迭代脚本必须有轮数上限防无限循环
- **嵌套包在子目录**：第一轮解压后，嵌套压缩包常出现在已解压出的**子目录**内（如 `222/222-Гайка.rar`），而非顶层——扫描必须用 `os.walk` 递归，不能只搜顶层
- **WinError 32**：Windows 文件锁（杀毒/搜索索引），不是脚本 bug；延迟重试是标准解法，重试脚本要记录"仍锁定"清单
- **pytest 环境**：项目 pytest 用 `smart-trade-ai/.venv/Scripts/python.exe -m pytest`（hermes venv 无 pytest）；按用户测试铁律只跑针对性冒烟单文件，不重跑全量
- 日志写 `scripts/logs/`，失败清单落盘（tab 分隔：路径\t原因）便于重试脚本复用

## 验证标准（交付物为准，符合用户测试铁律）
- 全目录扫描 .7z 数 = 0
- 抽查关键目录确认解压产物落盘
- 原包删除量 = 成功解压数（日志可核对）

## 完整归档流程（解压后文件归组）

当用户要求「执行完整的归档流程」或「把文件按编号归档」时，此流程在解压完成后执行。目标：**零残留压缩包 + 零平放文件**。

### 触发条件
- 用户说「完整归档流程」「按编号归组」「按归档格式整理」
- 解压后发现大量平放文件（带 `№-` 前缀但未入子文件夹）
- 乱码文件名修复后需要重新归档（乱码期间可能遗漏归组）

### 核心策略：多轮渐进式归组

#### 第 1 轮：`№-` 前缀直接归组（主力）
```python
m = re.match(r'^(\d+)-(.+)', fname)
if m:
    num = m.group(1)
    shutil.move(src, f'{proj_path}/{num}/{fname}')
```
- 处理 ~90% 的文件
- 目标同名时 MD5 比较：相同→删源，不同→加 `_v2` 后缀

#### 第 2 轮：前导数字 + 已存在文件夹匹配
文件无 `-` 分隔但开头是长数字，且该数字的文件夹已存在：
```python
m = re.match(r'^(\d{4,})', fname)  # 1227229_01_00.TIF → 1227229
if m and m.group(1) in existing_folders:
    move_to_folder(...)
```

#### 第 3 轮：ч. 图纸号提取
俄文零件名中嵌有 `ч.XXXX` 图纸号：
```python
m = re.search(r'[чЧ]\s*\.\s*(\d+)', fname)  # Винт ч.71-У-44.01 → 71
```
⚠️ 仅在目标文件夹已存在时移动，不为此创建新文件夹。

#### 第 4 轮：非标准命名模式
| 模式 | 正则 | 示例 | 目标文件夹 |
|:-----|:-----|:-----|:-----|
| `img-NNNNNNNNNN-NNNN` | `img-(\d+)-` | `img-0907235822-0001.tif` | `0907235822/` |
| `MYSCAN_YYYYMMDD_NNNN` | `MYSCAN_(\d+)_` | `MYSCAN_20120503_0001.TIF` | `20120503/` |
| `scanNNN` | `scan(\d+)\.` | `scan400.tif` | `400/` |
| `СКNNNN` 图纸号 | `СК(\d+)` | `Болт СК1629.00.004.tif` | `1629/` |
| `МNNN` 图纸号 | `М(\d+)` | `М424.01.15 СБ.tif` | `424/` |

⚠️ img-/MYSCAN/scan 模式始终创建新文件夹（可能原本不存在）。

#### 第 5 轮：零件名归组
完全无编号但同零件多文件的，按零件名归入俄文名称文件夹：
```python
# Корпус с упорами 1~13.tif → Корпус с упорами/
# Гребенка выхода 1~2.tif → Гребенка выхода/
# Спецификация направляющая пуансона 1~2.jpg → Спецификация направляющая пуансона/
```
- 仅在 ≥2 个文件共享同一零件名时创建文件夹
- 单文件散件（如 `Untitled.pdf`、`Корпус.tif`）保留平放，不在报告中当作错误

### 清理操作
- `Thumbs.db`：直接删除（Windows 系统缩略图缓存）
- 空文件夹：归组完成后 `os.rmdir` 清理

### 验证标准
- 全目录 `os.walk` 扫描：0 个 .7z/.rar/.zip/.gz
- 各项目顶层 `os.listdir`：0 个文件（或仅剩已报告的无法归组散件）
- 交付报告含：各项目文件夹数 / 文件总数 / 压缩包残留 / 平放文件数
