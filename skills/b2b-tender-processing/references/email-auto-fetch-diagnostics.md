# 邮箱自动抓取「假阴性」排查流程（邮件已抓到但用户以为没抓）

用户问「为什么 XX 的询价没被自动抓取？」时，**先诊断再下结论，禁止直接重抓**。多数情况下邮件早已落盘，只是定时监控没有通知机制，用户感知不到。

## 架构速览（通用组件，路径按实际部署替换）

| 组件 | 典型位置 | 作用 |
|:--|:--|:--|
| 定时任务定义 | cron 配置（如 `cron/jobs.json`） | 每个被监控邮箱一个 job，间隔 30m，`no_agent: true`（纯脚本，不走 LLM） |
| 监控脚本 | `monitor_<邮箱>_email.py` | 定时 IMAP 搜 `SINCE yesterday`，比对 `last_uid` 找新邮件，有新邮件才调抓取工具 |
| 监控断点 | `.<邮箱>_check_state.json` | `{"last_uid": N}`，只记录成功拉取后的最新 UID |
| 定时执行日志 | `cron/output/<job_id>/<时间戳>.md` | 每次运行的 stdout 摘要（新增几封、发件人、询价命中数） |
| 抓取工具 | `fetch_inbox.py`（或本 skill 的 mail_lib） | 通用 IMAP 拉取，断点续传，自动归类 招标_/询价/ |
| 抓取断点 | 抓取工具的 `state.json` | 每账号 `INBOX_done_uids`（已下载 UID 列表）+ 邮件元数据（主题/发件人/日期/附件） |
| 落盘目录 | `<邮件结果根目录>/<YYYYMMDD>_<邮箱>/` | eml/ + attachments/ + 索引 + 招标_<标段>/ + 询价/ |

## 排查四步（按序）

1. **查定时任务日志**（最快，先看这个）：按日期 grep 对应 job 的输出。
   命中特征：日志含「新增 N 封邮件」+ 发件人/主题 +「询价(RFQ): 命中 X 封 → 询价/」→ **证明已自动抓取**。
2. **查监控基线**：读 `.<邮箱>_check_state.json` 的 `last_uid`。
   - `last_uid == 服务器最新 UID` → 监控认为无新邮件（已全部处理过），不是故障。
3. **查磁盘落盘**：`find <邮件结果根目录> -name "<UID>*" -o -iname "*<主题关键词>*"`。eml + attachments 都在 → 已抓取。
4. **对照抓取断点**：读抓取工具的 `state.json`，确认该 UID 在 `INBOX_done_uids` 里（meta 里有主题/日期可反查）。

**结论规则**：日志显示已抓 + 磁盘有文件 → 向用户报告「已自动抓取 + 时间 + 位置 + 已归入询价/」，不重抓。

## 陷阱与边界

- **自动抓取 ≠ 自动通知**：监控脚本只写日志 + 落盘，不推送用户。邮件可能落盘数天而用户毫不知情——这是架构的既定行为，不是 bug。向用户解释时明确这一点。
- **任何抓取前必查本地**：**抓取动作执行之前**先做内容去重，不要抓完再整理。三步查重：① 按 UID grep 邮件结果目录；② 按主题/发件人关键词 grep；③ 附件 md5 比对。已存在的直接复用，禁止重复下载（出险案例：手动抓某客户邮件未先查本地，把数日前已落盘的邮件重抓进新目录，同一封存 3 处，还误导用户以为此前从未抓过）。
- **定时日志缺失 ≠ 没抓**：磁盘落盘的目录 mtime 无对应定时日志，说明那批是**手动跑抓取工具**抓的。判断"谁抓的"：目录 mtime 有无对应定时日志。
- **脚本超时是单点故障**：监控挂一次不影响后续——下次运行 `SINCE yesterday` 窗口仍能兜住，不会永久丢失。
- **主题归类与抓取是两回事**：监控脚本的主题正则只匹配招标关键词（tender/конкурс/标段号），无标段号的纯产品询价主题会被归为「其他邮件」，但**仍会触发拉取**并进入抓取工具的正文 RFQ 归类（正文含 запрос/коммерческое предложение 等词）→ 落到 询价/。日志里看到「其他邮件」不要误判为没抓。

## 出险案例复盘（某品牌产品询价，多封转发）

用户问「为什么这些询价没被自动抓取？」，实际全部已抓：

- 原始询价 + 同事转发：手动跑抓取工具落盘（无定时日志，无人通知）；
- 后续转发两封：定时任务自动抓取（日志为证），但只写日志文件，用户不翻看不到；
- 用户随后手动重抓，制造了「从未抓过」的错觉，同一封邮件落盘 3 处。

教训：先按「排查四步」拿到证据再回话；证据齐了就直接报「已抓 + 位置」，不要重抓。
